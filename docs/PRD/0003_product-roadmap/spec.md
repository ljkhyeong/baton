# PRD-0003: BATON 제품 개발 우선순위

- 상태: 계획
- 작성일: 2026-07-26
- 대상: 그룹 스터디 파일럿 안정화 이후의 제품 개발 순서

## 1. 문서 목적

이 문서는 현재 구현 계약이 아니라 BATON의 다음 개발 우선순위와 단계별 완료 기준을 기록한다.

- 현재 제품 동작과 범위는 [PRD-0001](../0001_product-baseline/spec.md)이 소유한다.
- 구현된 HTTP 계약은 [PRD-0002](../0002_api-contract/spec.md)가 소유한다.
- 이 문서에 있는 기능명, 상태 후보와 연동 방식은 해당 기능의 요구사항과 API 계약이 채택되기 전까지 계획이다.
- 파일럿 관찰 결과에 따라 같은 우선순위 안의 순서는 바뀔 수 있다.

## 2. 우선순위 원칙

BATON은 다음 순서로 개발한다.

1. 현재 그룹 스터디가 안전하게 반복 사용하지 못하게 하는 문제를 먼저 없앤다.
2. 매주 반복되는 수동 운영을 줄인다.
3. 역할 교대와 조직 기억의 단절을 예방하는 BATON 고유 가치를 강화한다.
4. 한정된 공유 링크에서 OIDC 계정·session·초대로 단계적으로 전환하고, 검증한 신원에
   최소 권한을 연결한다.
5. 외부 연동, 분석과 AI 보조는 신뢰할 수 있는 운영 데이터가 쌓인 뒤 추가한다.

기능 수보다 다음 제품 신호를 우선한다.

- 담당자가 없어 빠지는 책임을 더 일찍 발견하는가
- 반복 운영을 준비하는 시간이 줄어드는가
- 과거 결정의 이유를 더 빨리 찾는가
- 다음 담당자가 질문해야 하는 양과 시행착오가 줄어드는가

## 3. 우선순위 요약

| 우선순위 | 개발 묶음 | 기대 결과 |
| --- | --- | --- |
| P0 | 파일럿 안정화 | 키보드, 모바일, 네트워크와 브라우저 저장소 실패에서도 핵심 흐름을 안전하게 완료한다. |
| P1 | 구성원·시즌 생명주기 | 운영 중 구성원과 시즌을 관리하고 다음 시즌으로 기록을 이어 간다. |
| P1 | 회차·마감 자동화 | 반복 회차와 실제 마감을 자동으로 관리하고 지연을 판정한다. |
| P1 | 바통 전달·수락 | 역할 교대를 양쪽 담당자가 확인하는 명시적 흐름으로 만든다. |
| P2 | 조직 연속성 레이더 | 앞으로 운영이 끊길 가능성이 있는 역할과 기록을 먼저 보여 준다. |
| P2 | 기록 탐색 | 결정, 바통과 자료를 역할과 시간 흐름으로 다시 찾는다. |
| P3 | 계정·초대·권한·감사 | 공유 키를 사용자별 신원과 최소 권한 모델로 대체한다. |
| P3 | 다중 조직 탐색 | 한 사용자가 여러 팀과 시즌을 전환해 운영한다. |
| P3 | 알림·외부 연동 | 확정된 운영 신호를 선택한 외부 채널로 전달한다. |
| P4 | 템플릿·분석·AI 보조 | 검증된 운영 패턴을 재사용하고 축적된 기록을 보조적으로 활용한다. |

## 4. P0 — 파일럿 안정화

새 제품 도메인을 추가하기 전에 현재 핵심 흐름의 사용성과 실패 복구를 마무리한다.

### 완료된 범위

- 공용 dialog와 모바일 drawer의 초기 focus, focus trap, `Escape` 닫기와 opener focus 복귀
- 닫힌 모바일 inspector의 keyboard·screen reader 접근 차단
- tablist의 방향키 이동, roving `tabIndex`와 tabpanel 연결
- 동시 수정 충돌 뒤 최신 projection을 확인하기 전 오래된 폼의 재편집·재제출 차단
- 생성 요청 중 닫기·재진입과 mutation observer 유실 방지
- 온보딩 생성과 복구 기록 폐기의 탭 간 직렬화
- 콘텐츠 생성의 요청 결과 확정 전 탭 간 직렬화와 경쟁 탭 무전송
- 접근 키 변경 journal의 검증 삭제와 tombstone 기반 재사용 차단
- 브라우저 위치와 무관한 시즌 IANA 시간대의 달력 날짜 기준 시즌 진행률과 종료 안내
- fetch 거부, 요청 timeout과 2xx 응답 파싱 실패의 공용 client 오류 표준화와 멱등 journal 보존
- 온보딩·콘텐츠 생성·접근 키 변경 journal의 공통 오류 확정성 분류와 snapshot 검증 cleanup
- 온보딩의 복구 snapshot 변경·재생 만료 확인 경계와 콘텐츠 생성의 성공·결정적 종료 cleanup 실패 재전송 차단
- 접근 키 변경 journal 생성·요청·cleanup의 팀별 탭 간 직렬화와 경쟁 탭 무전송
- 작은 보조 문구·placeholder·경고의 `4.5:1` 이상 대비와 밝은 본문·어두운 navigation의 keyboard focus `3:1` 이상 대비
- 보관함 summary, 바통 tabpanel과 시각적으로 감춘 checkbox의 keyboard focus 표시

### 남은 개발 범위

- 외부 health sentinel 실제 공개 URL, 첫 예약 실행과 알림 수신 검증
- 실제 파일럿 데이터 입력 전 백업 생성과 별도 환경 복구 리허설

### 완료 기준

- 키보드만으로 주요 화면, dialog, drawer와 tab을 이동하고 작업할 수 있다.
- 작은 보조 문구와 경고는 `4.5:1`, keyboard focus 표시는 `3:1` 이상의 색 대비로 구분된다.
- 네트워크와 브라우저 저장소가 실패해도 중복 리소스나 해소할 수 없는 pending 기록을 만들지 않는다.
- 시즌에 설정한 시간대의 시작일과 종료일에 진행률 경계가 일관된다.
- 외부에서 파일럿 장애를 감지하고 담당자가 알림을 받는 경로를 한 번 이상 확인한다.

## 5. P1 — 반복 운영을 완성하는 기능

### 5.1 구성원·시즌 생명주기

#### 완료된 범위

- 기존 팀의 구성원 추가. 팀 안에서 이름을 유일하게 유지하고, 응답이 유실되면 같은 멱등 요청으로 생성 결과를 확인한다.
- 구성원 표시 이름 수정과 가역적 활동 종료·재활성화. 기존 역할·결정 참조는 보존하고 새 담당자·작성자 선택에서만 활동 종료 구성원을 제외한다.
- 시즌 이름·기간 수정과 명시적 종료·재개. 종료 시즌은 읽기 전용으로 조회한다.
- 같은 팀의 서버 권위 시즌 목록 전환과 종료 시즌 탐색.
- 이전 시즌에서 선택한 역할·루틴 정의를 새 UUID로 복사하는 멱등한 다음 시즌 시작.
- 역할 담당자·담당 기간과 실행 상태는 초기화하고, 과거 회차·실행·결정·바통·자료는 원본 시즌에 보존하는 전환 규칙.
- 다음 시즌 생성 응답 유실을 복구하는 팀 단위 durable journal과 탭 간 Web Lock.

영구 삭제와 과거 사실의 재작성은 이 단계의 기본 해법으로 사용하지 않는다.

#### 완료 기준

- 운영자가 DB나 초기 온보딩을 직접 다루지 않고 구성원 변경과 다음 시즌 시작을 완료한다.
- 이전 시즌 기록은 조회할 수 있고 새 시즌의 실행 상태와 섞이지 않는다.

### 5.2 회차·마감 자동화

#### 완료된 범위

- 시즌별 IANA 시간대. 기존·최초 시즌은 `Asia/Seoul`을 기본으로 하고 다음 시즌은 원본 시간대를 이어 받는다.
- 시즌당 하나인 주간·격주 일정, `0..30`일 선행 생성과 다음 발생일 커서.
- 사람이 읽는 기한 문구와 분리된 모임 날짜 기준 실제 마감 규칙, 실행별 UTC `deadlineAt` 스냅샷.
- 루틴의 `UNSCHEDULED`·`PLANNED`·`IN_PROGRESS`·`OVERDUE`·`COMPLETED`와 회차의 예정·진행·지연·완료 파생 상태.
- 기본 `PT1M` poll에서 데이터베이스 상태를 수렴시키는 자동 생성. 한 tick은 모든 활성 시즌 후보와 시즌별 최대 8개 발생을 처리한다.
- `Team` 공유 잠금 뒤 `Season` 배타 잠금, 발생일 유일 제약과 전진 커서를 이용한 중복 없는 재실행.
- 자동 회차 이름·날짜의 직접 수정 금지와 기록을 유지하는 가역 보관·복원.
- 오늘 화면의 지연 우선 표시와 관련 회차 자동 선택, 운영 화면의 일정 설정·일시 중지·재개.
- Java `atZone`의 DST gap 전진·overlap 앞선 오프셋 정책과 backend `Clock` 경계 테스트.

외부 메시징·메일·캘린더 알림은 이 단계에 포함하지 않으며 P3의 계정·신원과 실제 채널 요구가 확인된 뒤 결정한다.

#### 완료 기준

- 정해진 기간 동안 운영자가 매번 수동으로 회차를 만들지 않아도 된다.
- 같은 schedule을 재실행해도 회차가 중복되지 않는다.
- 시간대와 마감 경계가 backend `Clock` 기반 테스트로 고정된다.

### 5.3 바통 전달·수락

#### 완료된 범위

- 역할과 분리한 역할 바통 이력과 `PREPARING → TRANSFERRED → ACCEPTED` 또는 `CANCELLED` 상태 흐름
- 준비 시 이전·다음 담당자와 수락 뒤 적용할 담당 기간 고정
- 이전 담당자 명의의 전달 확인과 다음 담당자 명의의 수락 확인
- 수락 전 이전 담당자 명의의 취소와 다음 담당자 예약 해제
- 전달 시 활성 바통 항목 수, 미완료 항목 수와 연결 자료 수 스냅샷
- 바통 항목이 없거나 미완료 항목이 있거나 자료가 없을 때 명시적인 위험 경고 확인
- 수락 transaction에서 역할의 현재·다음 담당자와 담당 기간을 함께 전환
- 역할마다 하나의 열린 바통만 허용하고 완료·취소한 과거 이력은 보존
- 준비 중에는 역할의 담당자·담당 기간을, 전달 뒤에는 역할·바통 항목·자료 전체를 수락 또는 취소 전까지 동결
- 열린 바통이 있는 시즌의 종료와 다음 시즌 시작 차단

session 방식의 `confirmedByMemberId`는 현재 account에 결속된 활동 중 구성원과 같아야 한다.
레거시 공유 키 방식에서는 계속 특정 구성원 명의로 확인했다고 선언하는 값일 뿐 실제
로그인 행위자 감사 증거는 아니다. 역할별 세부 권한과 변경 감사 이력은 P3 후속 범위다.

#### 완료 기준

- 실제 역할 교대 한 건을 BATON 안에서 준비부터 수락까지 수행한다.
- 역할의 책임, 루틴, 결정, 자료와 남은 작업이 교대 뒤에도 연결된다.

## 6. P2 — BATON의 차별화

### 6.1 조직 연속성 레이더

처음에는 설명 가능한 규칙으로 구현하고 AI 판단에 의존하지 않는다.

#### 신호 후보

- 현재 담당자가 없는 역할
- 담당 종료가 임박했지만 다음 담당자가 없는 역할
- 위험 신호는 있지만 책임, 자료 또는 바통 준비가 부족한 역할
- 여러 회차에서 반복해 지연되는 루틴
- 역할 교대가 가까운데 완료되지 않은 바통 항목
- 오래 확인되지 않은 핵심 역할 자료

#### 완료 기준

- 각 신호가 발생한 이유와 사용자가 취할 다음 행동을 함께 설명한다.
- 파일럿 사용자가 실제로 놓칠 뻔한 책임이나 인수인계 공백을 한 번 이상 사전에 발견한다.

### 6.2 기록 탐색

#### 계획 범위

- 결정, 바통 항목과 역할 자료의 통합 검색
- 역할별 결정·자료·바통 시간 흐름
- 활성·보관 상태와 기간 필터

#### 완료 기준

- 사용자가 특정 결정의 결과, 이유와 관련 역할을 짧은 탐색 흐름 안에서 다시 찾는다.

## 7. P3 — 여러 조직으로 확장

### 7.1 계정·초대·권한·감사

#### 완료된 기반

- 로그인 공급자와 분리된 BATON 내부 `UserAccount` UUID
- 기존 roster를 보존하고 같은 팀의 계정·구성원 중복 결속을 막는
  `MemberIdentityBinding`
- Google OIDC Authorization Code + PKCE와 issuer·subject 외부 신원 결속
- provider token을 저장하지 않는 MySQL opaque session, idle 30분·absolute 12시간 만료와
  CSRF가 필요한 session 변경
- 외부 edge에서 차단한 내부 운영 경로의 1시간 단일 사용 owner bootstrap invitation과
  기존 구성원의 팀별 유일 `OWNER` 결속
- 현재 활성 `OWNER`가 24시간 일반 구성원 invitation을 멱등 발급·조회·폐기하고 로그인
  사용자가 미리보기 뒤 수락해 기존 roster에 `MEMBER`로 결속하는 API와 웹 화면
- production identity secret·OIDC callback fail-closed와 session·OIDC·invitation 값의
  Caddy access log 비노출
- 활성 구성원과 역할 자료를 서버에서 다시 확인하는 최대 5분 `participant` ROUND
  참여권, RS256/JWKS key ring, room-scoped `HttpOnly` cookie와 same-origin edge
- 역할 자료 context와 직접 초대 fallback, `grant → TURN → WebSocket`, TURN 갱신과
  signaling 재연결 전 새 grant를 보장하는 브라우저 수명주기
- access-key header가 없는 일반 workspace 요청을 활동 중 session 구성원 결속으로
  판정하고 session 변경에 CSRF를 강제하는 application·web 경계
- 레거시 접근 키와 session 권한을 상호 배타적으로 선택하고 실패 뒤 다른 방식으로
  fallback하지 않는 마이그레이션 호환
- origin-wide `localStorage` 접근 키 저장 제거, account별 workspace cache와
  로그아웃·account 교체 시 workspace·ROUND 진입 문맥 정리

이 기반은 [ADR-0016](../../ADR/0016_google-oidc-session-owner-bootstrap/adr.md),
[ADR-0017](../../ADR/0017_owner-issued-member-invitations/adr.md)과
[ADR-0018](../../ADR/0018_round-participation-grants/adr.md),
[ADR-0019](../../ADR/0019_session-based-workspace-authorization/adr.md)가 소유한다.
활성 `OWNER|MEMBER`는 세부 권한 행렬 전까지 기존 파일럿 workspace 범위를 함께 사용한다.
다만 session 결정의 `authorMemberId`와 역할 바통의 `confirmedByMemberId`는 현재 account의
결속 구성원과 일치시킨다. 레거시 키 방식의 같은 필드는 실제 로그인 행위자 감사로
과장하지 않는다.

#### 남은 개발 범위

- 계정 비활성화·탈퇴·복구와 잘못된 결속의 운영 복구
- 팀·시즌·역할별 최소 권한과 사용자별 변경 주체·감사 이력
- 신규 workspace 생성 account와 명시한 owner roster 구성원의 원자 결속
- 레거시 fragment·회전·운영자 복구의 종료 조건과 공유 키 완전 폐기
- 여러 OIDC 공급자 연결과 한 사용자의 provider account 연결 정책

ROUND 참여권의 `sub`에는 provider subject나 `Member` UUID가 아니라 BATON 내부 account
UUID를 사용한다. 구현된 참여권은 활성 구성원 결속과 대상 역할 자료 권한을 서버에서 다시
확인한 뒤 `participant`만 발급한다. `host`는 별도 권한 행렬이 채택될 때까지 보류한다.

#### 완료 기준

- 실제 사용자가 로그인하고 invitation을 수락해 기존 roster와 결속된다.
- 공유 키를 사용자 신원으로 사용하지 않고 모든 account 권한 판단이 server-side membership에
  근거한다.
- 초대 만료·폐기·재사용, session 만료·CSRF와 계정 복구 경계가 실제 브라우저와 MySQL에서
  검증된다.

### 7.2 다중 조직 탐색

- 사용자가 참여한 팀 목록
- 최근 활동과 초대 대기 상태
- 팀·시즌이 포함된 cache와 URL 경계

공유 키 파일럿에서 한 팀 안의 시즌 선택·종료 시즌 탐색과 팀·시즌 URL·cache 경계는 P1에서 구현했다. 이 단계는 계정 신원을 기준으로 여러 팀을 한 목록에서 전환하는 범위만 소유한다.

### 7.3 알림·외부 연동

- 실제 마감, 지연, 역할 공백과 바통 전달 이벤트
- 사용자 또는 역할 단위의 알림 선호
- 캘린더와 메시징·메일 채널 연동
- 중복 발송 방지, 재시도와 전달 결과 추적

알림 채널은 계정·신원과 실제 파일럿 요구가 확인된 뒤 선택한다.

## 8. P4 — 재사용과 보조 기능

- 스터디, 동아리, 위원회와 TF의 역할·루틴 시작 템플릿
- 반복 지연, 역할 공백과 인수인계 준비도 추세
- 결정과 바통 기록의 검색·요약 보조
- 사용자가 확인하는 초안 형태의 운영 개선 제안

AI는 조직 결정을 대신하지 않고 검색, 요약과 누락 후보 제시에만 사용한다.

## 9. 병행 기술 과제

기능 개발과 별도로 다음 구조 개선을 작은 변경으로 병행한다.

- `WorkspaceService`에서 인증, 콘텐츠 멱등성, projection 조립과 기능별 use case 분리
- 대형 workspace UI와 modal을 기능 소유 단위로 분리
- 유스케이스·REST Docs·Playwright 대형 테스트를 기능 경계로 분리
- persistence 충돌 예외의 원인 보존과 공통 변환
- 예상하지 않은 서버 오류의 안정적인 오류 코드와 request ID
- outbound adapter 독립성을 실제로 검증하는 architecture test
- Gradle 10 전환 전에 REST Docs OpenAPI plugin의 deprecated API 제거
- 데이터가 늘기 전 workspace projection의 조건부 조회, pagination 또는 갱신 방식 재검토

구조 분리는 동작 변경과 섞지 않고 각 기능을 추가하기 직전의 가장 가까운 경계부터 수행한다.

## 10. 당장 개발하지 않는 범위

- 자체 채팅과 화상회의
- 범용 문서 편집기와 파일 저장소
- 출석, 회계, 급여, 평가와 학사 행정 전체
- 복잡한 전자결재
- 모든 프로젝트 관리 기능
- AI의 자동 의사결정

실제 파일럿에서 BATON의 핵심 흐름과 직접 연결된 요구가 확인되기 전에는 이 범위를 확장하지 않는다.

## 11. 실행 순서

현재 기준의 권장 실행 순서는 다음과 같다.

1. 남은 P0 운영 검증
2. 실제 OIDC·외부 TURN·dual-key rotation을 포함한 ROUND HTTPS full-stack 실입장 검증
3. 조직 연속성 레이더
4. 결정·바통·자료 탐색
5. 계정 권한·감사와 다중 팀 탐색
6. 알림과 외부 연동
7. 템플릿·분석·AI 보조

각 단계는 사용자 흐름, 실패 경계, 데이터 보존 규칙과 완료 기준을 별도 요구사항으로 확정한 뒤 API 계약과 함께 구현한다.
