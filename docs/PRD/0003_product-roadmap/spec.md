# PRD-0003: BATON 제품 개발 우선순위

- 상태: 계획
- 작성일: 2026-07-26
- 대상: 그룹 스터디 파일럿 안정화 이후의 제품 개발 순서

## 1. 문서 목적

이 문서는 현재 개발 우선순위와 단계별 완료 기준을 기록한다. 구현 완료와 운영 검증은 각 절에서 구분한다.

- 현재 제품 동작과 범위는 [PRD-0001](../0001_product-baseline/spec.md)이 소유한다.
- 구현된 HTTP 계약은 [PRD-0002](../0002_api-contract/spec.md)가 소유한다.
- 이 문서에 있는 기능명, 상태 후보와 연동 방식은 해당 기능의 요구사항과 API 계약이 채택되기 전까지 계획이다.
- 파일럿 관찰 결과에 따라 같은 우선순위 안의 순서는 바뀔 수 있다.

## 2. 우선순위 원칙

BATON은 다음 순서로 개발한다.

1. 현재 그룹 스터디가 안전하게 반복 사용하지 못하게 하는 문제를 먼저 없앤다.
2. 매주 반복되는 수동 운영을 줄인다.
3. 담당자 교대 때 업무 기록이 빠지지 않게 한다.
4. 공유 링크 파일럿을 검증한 뒤 팀별 계정 권한으로 전환한다.
5. 외부 연동, 분석과 AI 보조는 신뢰할 수 있는 운영 데이터가 쌓인 뒤 추가한다.

기능 수보다 다음 효과를 우선한다.

- 담당자가 없어 빠지는 책임을 더 일찍 발견하는가
- 반복 운영을 준비하는 시간이 줄어드는가
- 과거 결정의 이유를 더 빨리 찾는가
- 다음 담당자가 질문해야 하는 양과 시행착오가 줄어드는가

## 3. 우선순위 요약

| 우선순위 | 개발 과제 | 기대 결과 |
| --- | --- | --- |
| P0 | 파일럿 안정화 | 키보드, 모바일, 네트워크와 브라우저 저장소 실패에서도 핵심 흐름을 안전하게 완료한다. |
| P1 | 구성원·시즌 생명주기 | 운영 중 구성원과 시즌을 관리하고 다음 시즌으로 기록을 이어 간다. |
| P1 | 회차·마감 자동화 | 반복 회차와 실제 마감을 자동으로 관리하고 지연을 판정한다. |
| P1 | 인수인계 전달·수락 | 역할 교대를 양쪽 담당자가 확인하는 명시적 흐름으로 만든다. |
| P2 | 운영 점검 | 담당자 공백·업무 지연·인수인계 미완료를 먼저 보여 준다. |
| P2 | 기록 탐색 | 결정, 인수인계와 자료를 역할과 시간 흐름으로 다시 찾는다. |
| P3 | 계정 전환·초대·권한·감사 | 계정 신원을 기존 구성원과 연결하고 팀별 관리자·구성원·열람자 권한으로 전환한다. |
| P3 | 다중 조직 탐색 | 한 사용자가 여러 팀과 시즌을 전환해 운영한다. |
| P3 | 알림·외부 연동 | 확정된 운영 신호를 선택한 외부 채널로 전달한다. |
| P4 | 템플릿·분석·AI 보조 | 검증된 운영 패턴을 재사용하고 축적된 기록을 보조적으로 활용한다. |

## 4. P0 — 파일럿 안정화

새 제품 도메인을 추가하기 전에 현재 핵심 흐름의 사용성과 실패 복구를 마무리한다.

### 완료된 범위

- 공용 대화상자와 모바일 서랍의 초기 포커스, 포커스 가두기, `Escape` 닫기와 호출 요소 포커스 복귀
- 닫힌 모바일 역할 상세의 키보드·화면 읽기 도구 접근 차단
- 탭 목록의 방향키 이동, 순회 `tabIndex`와 탭 패널 연결
- 동시 수정 충돌 뒤 최신 프로젝션을 확인하기 전 오래된 폼의 재편집·재제출 차단
- 생성 요청 중 닫기·재진입과 `MutationObserver` 유실 방지
- 온보딩 생성과 복구 목록에서 삭제의 탭 간 직렬화
- 콘텐츠 생성의 요청 결과 확정 전 탭 간 직렬화와 경쟁 탭 무전송
- 접근 키 변경 임시 기록의 Web Storage 저장·삭제 실패 처리와 재사용 차단
- 브라우저 위치와 무관한 시즌 IANA 시간대의 달력 날짜 기준 시즌 진행률과 종료 안내
- `fetch` 실패, 요청 시간 초과와 2xx 응답 파싱 실패를 공통 오류로 처리하고 재시도용 임시 기록 유지
- 온보딩·콘텐츠 생성·접근 키 변경 오류를 재시도·새 요청·결과 확인 필요로 분류하고 임시 기록 정리
- 온보딩 복구 기록 변경·재처리 결과 만료 시 기존 결과 확인, 콘텐츠 생성 성공·재시도 불가 오류 후 임시 기록 삭제 실패 시 새 요청 차단
- 접근 키 변경의 임시 기록 생성·요청·삭제를 팀별로 한 탭에서만 실행하고 다른 탭의 전송 차단
- 작은 보조 문구·자리표시자·경고의 `4.5:1` 이상 대비와 밝은 본문·어두운 탐색 영역의 키보드 포커스 `3:1` 이상 대비
- 보관함 요약, 인수인계 탭 패널과 시각적으로 감춘 체크박스의 키보드 포커스 표시
- 폐기 가능한 프로덕션 이미지·MySQL에서 원본 백업·복구 스크립트로 스냅샷 롤백, 모든 과거 키 폐기, 팀별 최신 시즌 복구·멱등 동일 재처리, 새 키의 조회·변경과 재백업을 검증하는 자동 복구 리허설
- CAL·WATCH 전달 상태를 Prometheus로 노출하고 지표 갱신 정체·영구 실패·만료 임대만 실패로 판정하는 읽기 전용 호스트 점검

### 남은 개발 범위

- 외부 서비스 상태 감시 실제 공개 URL, 첫 예약 실행과 알림 수신 검증
- 실제 파일럿 데이터 입력 전 외부 암호화 백업 생성과 `crypt` 원격 저장소에서 내려받은 파일의 별도 환경 복구 리허설

### 완료 기준

- 키보드만으로 주요 화면, 대화상자, 서랍과 탭을 이동하고 작업할 수 있다.
- 작은 보조 문구와 경고는 `4.5:1`, 키보드 포커스 표시는 `3:1` 이상의 색 대비로 구분된다.
- 네트워크와 브라우저 저장소가 실패해도 중복 리소스나 해소할 수 없는 대기 기록을 만들지 않는다.
- 시즌에 설정한 시간대의 시작일과 종료일에 진행률 경계가 일관된다.
- 외부에서 파일럿 장애를 감지하고 담당자가 알림을 받는 경로를 한 번 이상 확인한다.

## 5. P1 — 반복 운영을 완성하는 기능

### 5.1 구성원·시즌 생명주기

#### 완료된 범위

- 기존 팀의 구성원 추가. 팀 안에서 이름을 유일하게 유지하고, 응답이 유실되면 같은 멱등 요청으로 생성 결과를 확인한다.
- 구성원 표시 이름 수정과 가역적 활동 종료·재활성화. 기존 역할·결정 참조는 보존하고 새 담당자·작성자 선택에서만 활동 종료 구성원을 제외한다.
- 시즌 이름·기간 수정과 명시적 종료·재개. 종료 시즌은 읽기 전용으로 조회한다.
- 같은 팀의 서버에서 관리하는 시즌 목록 전환과 종료 시즌 탐색.
- 이어받은 역할의 상세에서 이전 시즌 목적·책임·주의사항·자료·결정 이유·인수인계 항목 조회와 선택한 자료의 현재 역할 연결. 이전 시즌은 펼칠 때 조회하고 원본 기록은 유지한다.
- 이전 시즌에서 선택한 역할·반복 업무 정의를 새 UUID로 복사하는 멱등한 다음 시즌 시작.
- 역할 담당자·담당 기간과 실행 상태는 초기화하고, 과거 회차·실행·결정·인수인계·자료는 원본 시즌에 보존하는 전환 규칙.
- 다음 시즌 생성 응답 유실을 복구하는 팀 단위 내구 저널과 탭 간 Web Lock.

영구 삭제와 과거 사실의 재작성은 이 단계의 기본 해법으로 사용하지 않는다.

#### 완료 기준

- 운영자가 DB나 초기 온보딩을 직접 다루지 않고 구성원 변경과 다음 시즌 시작을 완료한다.
- 이전 시즌 기록은 조회할 수 있고 새 시즌의 실행 상태와 섞이지 않는다.

### 5.2 회차·마감 자동화

#### 완료된 범위

- 시즌별 IANA 시간대. 기존·최초 시즌은 `Asia/Seoul`을 기본으로 하고 다음 시즌은 원본 시간대를 이어 받는다.
- 시즌당 하나인 주간·격주 일정, `0..30`일 선행 생성과 다음 발생일 커서.
- 사람이 읽는 기한 문구와 분리된 모임 날짜 기준 실제 마감 규칙, 실행별 UTC `deadlineAt` 스냅샷.
- 반복 업무의 `UNSCHEDULED`·`PLANNED`·`IN_PROGRESS`·`OVERDUE`·`COMPLETED`와 회차의 예정·진행·지연·완료 파생 상태.
- 기본 `PT1M` 폴링에서 데이터베이스 상태를 수렴시키는 자동 생성. 한 틱은 모든 활성 시즌 후보와 시즌별 최대 8개 발생을 처리한다.
- `Team` 공유 잠금 뒤 `Season` 배타 잠금, 발생일 유일 제약과 전진 커서를 이용한 중복 없는 재실행.
- 자동 회차 이름·날짜 정정과 이번 회차 건너뛰기·복원. 원래 발생일, 실행 ID·완료 상태와 다음 반복 일정은 보존하고 날짜 변경 때 복사된 규칙으로 실제 마감을 다시 계산한다.
- 사용하지 않는 반복 업무 정의를 과거 실행과 분리해 보관·복원하고 미래 수동·자동 회차와 다음 시즌 복사에서 제외하는 생명주기.
- 오늘 화면의 지연 우선 표시와 관련 회차 자동 선택, 운영 화면의 일정 설정·일시 중지·재개.
- Java `atZone`의 DST 간격 전진·중첩 시 앞선 오프셋 정책과 백엔드 `Clock` 경계 테스트.

외부 메시징·메일·캘린더 알림은 이 단계에 포함하지 않으며 P3의 계정·신원과 실제 채널 요구가 확인된 뒤 결정한다.

#### 완료 기준

- 정해진 기간 동안 운영자가 매번 수동으로 회차를 만들지 않아도 된다.
- 같은 일정을 재실행해도 회차가 중복되지 않는다.
- 시간대와 마감 경계가 백엔드 `Clock` 기반 테스트로 고정된다.

### 5.3 인수인계 전달·수락

#### 완료된 범위

- 역할과 분리한 역할 인수인계 이력과 `PREPARING → TRANSFERRED → ACCEPTED` 또는 `CANCELLED` 상태 흐름
- 준비 시 이전·다음 담당자와 수락 뒤 적용할 담당 기간 고정
- 이전 담당자 명의의 전달 확인과 다음 담당자 명의의 수락 확인
- 수락 전 이전 담당자 명의의 취소와 다음 담당자 예약 해제
- 전달 시 활성 인수인계 항목 수, 미완료 항목 수와 연결 자료 수 스냅샷
- 인수인계 항목이 없거나 미완료 항목이 있거나 자료가 없을 때 명시적인 위험 경고 확인
- 수락 트랜잭션에서 역할의 현재·다음 담당자와 담당 기간을 함께 전환
- 역할마다 하나의 열린 인수인계만 허용하고 완료·취소한 과거 이력은 보존
- 준비 중에는 역할의 담당자·담당 기간을, 전달 뒤에는 역할·인수인계 항목·자료 전체를 수락 또는 취소 전까지 동결
- 열린 인수인계가 있는 시즌의 종료와 다음 시즌 시작 차단

파일럿의 `confirmedByMemberId`는 공유 키를 가진 요청자가 특정 구성원 명의로 확인했다고 선언하는 값이다. 실제 로그인 사용자의 신원을 인증한 감사 증거는 아니며, 사용자별 인증·권한은 P3에서 다룬다.

#### 완료 기준

- 실제 역할 교대 한 건을 BATON 안에서 준비부터 수락까지 수행한다.
- 역할의 책임, 반복 업무, 결정, 자료와 남은 작업이 교대 뒤에도 연결된다.

## 6. P2 — 업무 누락 점검과 기록 검색

### 6.1 업무 점검

처음에는 설명 가능한 규칙으로 구현하고 AI 판단에 의존하지 않는다.

#### 완료된 범위

- 현재 담당자가 없거나 활동을 종료한 역할
- 시즌 현지 오늘부터 14일 안에 담당이 끝나거나 이미 끝났지만 다음 담당자가 없거나 활동을 종료했거나 현재 담당자와 같은 역할
- 주의사항은 있지만 담당 업무, 자료 또는 인수인계 준비가 부족한 역할
- 서로 다른 활성 회차에서 2회 이상 반복해 지연되는 반복 업무
- 후임만 정하고 실제 인수인계를 시작하지 않았거나, 7일 안에 새 담당이 시작되거나 이미 시작됐지만 전달·수락이 끝나지 않은 역할 인수인계
- 현재 담당 종료와 새 담당 시작 사이에 실제 공백이 생기는 역할 인수인계
- 활동 종료한 필수 참여자로 인해 현재 단계의 전달·수락을 진행할 수 없는 열린 역할 인수인계
- 전달 뒤 이전 담당자가 활동을 종료해 다음 담당자의 즉시 수락이 필요한 역할 인수인계
- 신호별 `CRITICAL`·`WARNING` 우선순위, 현재 기록에서 발생한 이유와 다음 행동
- 종료 시즌, 보관 회차와 보관 인수인계 항목을 조치가 필요한 신호에서 제외
- 기존 워크스페이스 프로젝션과 오늘 화면을 통한 서버 계산 결과 표시와 관련 역할·운영·인수인계 화면 이동

#### 남은 범위와 검증

- 파일럿 실사용에서 실제로 놓칠 뻔한 책임이나 인수인계 공백을 한 번 이상 사전에 발견하고, 오탐과 행동 문구를 조정한다.
- 자료별 수동 확인 기록과 선택적 재확인 주기를 제공한다. 시즌 날짜의 확인일 당일부터 기한을 표시하며, 오늘 화면의 재확인 목록과 역할 상세 이동을 제공한다. 업무 점검 신호나 외부 알림으로 전송하는 것은 별도 후속 범위다.

#### 완료 기준

- 각 신호가 발생한 이유와 사용자가 취할 다음 행동을 함께 설명한다.
- 파일럿 사용자가 실제로 놓칠 뻔한 책임이나 인수인계 공백을 한 번 이상 사전에 발견한다.

### 6.2 기록 탐색

#### 완료된 범위

- 현재 시즌 또는 요청 시 조회한 팀의 모든 시즌의 결정·인수인계 항목·역할 자료 통합 검색
- 기록 종류, 관련 역할, 활성·보관 상태와 시즌 시간대 기준 기간 필터
- 결정의 결과·이유·대안·작성자·관련 역할을 한 결과에서 확인
- 생성 시각 내림차순 시간 흐름과 V14 이전 인수인계·자료의 시각 미상 처리
- 활성 결과의 결정 원장·인수인계 문서·역할 화면 이동, 돌아온 뒤 검색 조건 유지와 보관 결과의 검색 맥락 유지
- 자료 URL 문자열과 외부 문서 본문을 검색 대상에서 제외
- 역할 자료의 보관 시각에 따라 활성·보관 기록을 구분하고 보관 자료도 탐색 결과에서 조회
- 데스크톱과 390px 모바일 탐색

#### 완료 기준

- 사용자가 특정 결정의 결과, 이유와 관련 역할을 짧은 탐색 흐름 안에서 다시 찾는다.

#### 남은 범위와 검증

- 첫 그룹 스터디에서 과거 결정 한 건의 결과·이유·관련 역할을 별도 설명 없이 다시 찾게 하고, 놓친 검색어·필터와 시각 미상 안내의 이해도를 기록한다.
- 워크스페이스 프로젝션 크기가 실제 응답·브라우저 비용 문제가 되기 전에는 서버 검색·페이지네이션을 추가하지 않는다. 규모 문제가 관찰되면 조건부 조회나 커서 검색 계약을 별도로 설계한다.

### 6.3 업무 설명 작성과 Markdown

역할, 결정, 반복 업무와 인수인계에 붙는 자세한 업무 설명은 Markdown 원문과 안전한 미리보기로 작성하는 방향을 채택한다. Notion 자체를 복제하는 범용 블록 편집기는 만들지 않는다.

#### 첫 적용 범위

- 결정의 이유와 대안에 일반 텍스트·Markdown 선택과 편집·미리보기를 제공한다. 굵게, 목록, 링크와 코드 서식을 사용할 수 있다. 기존 기록은 `PLAIN_TEXT`로 유지하고 명시적으로 `MARKDOWN`을 선택한 기록만 서식을 표시한다.
- 실제 사용 뒤 역할 목적과 반복 업무 상세로 확대
- 목록·검색 결과에는 Markdown 전체를 렌더링하지 않고 사용자가 보는 일반 텍스트 발췌문을 표시
- 긴 회고·회의록 요구가 반복되면 시즌·역할·작성자에 연결된 별도 `bodyMarkdown` 기록을 설계

#### 데이터와 보안 원칙

- 렌더링 HTML이 아니라 Markdown 원문을 기준 데이터로 저장한다.
- 원시 HTML, `iframe`, 스크립트와 `dangerouslySetInnerHTML`을 허용하지 않는다.
- 첫 버전은 `http`·`https` 링크만 허용하고 이미지 문법과 외부 임베드를 비활성화한다.
- 제목, 구성원 이름, 기한 레이블, 책임 배열과 인수인계 확인란 레이블은 구조화된 일반 텍스트로 유지한다.
- 기존 일반 텍스트를 조용히 Markdown으로 재해석하지 않는다. 기존 필드에 적용할 때는 명시적 형식 버전 또는 새 Markdown 필드와 마이그레이션 계약을 먼저 정한다.
- Markdown 링크는 WATCH 자동 감시 대상이 아니다. WATCH는 사용자가 명시적으로 만든 `RoleResource.url`만 점검한다.
- 검색은 Markdown 기호, 코드 블록 구분자와 링크 대상을 제외한 렌더링된 사용자 가시 텍스트를 기준으로 한다.

#### 단계 전환 조건

드래그 정렬, 중첩 블록, 멘션·임베드, 부분 변경 이력과 여러 사람의 동시 편집 요구가 파일럿에서 반복되고 레코드 단위 `409` 충돌이 실제 불편으로 확인될 때만 스키마 버전을 가진 별도 블록 문서를 검토한다.

## 7. P3 — 여러 조직으로 확장

### 7.1 계정·초대·권한·감사

#### 완료된 기반 범위

- 공급자 중립 `Account`와 Google OIDC·Naver OAuth2·자체 이메일 신원
- 동일 출처 서버 `HttpSession`, 동적 CSRF, 세션 고정 보호와 인증 요청률 제한
- 자체 이메일 비밀번호 재설정과 기존 계정 세션 무효화. 실제 SMTP 검증과 운영 활성화는 별도 작업으로 남아 있다.
- 계정 보안 화면의 로그인 방법 조회, 현재 비밀번호 확인 후 변경과 본인의 모든 기기 로그아웃
- 기존 `Member`를 계정에 명시적으로 연결하는 `AccountMembership` 영속 모델과 변경 API
- 현재 팀의 `AccountMembership` 조회와 구성원 관리 화면의 명시적 연결·새로고침 복구 흐름
- 계정·팀별 캐시 경계와 접근 키를 복제하지 않는 로그인·OAuth 콜백 복귀 경로
- 정규 ROUND 방 매핑·삭제 표식과 짧은 수명의 RS256 참여권·공개 JWK
- OAuth·SMTP·아웃박스 암호화 키·ROUND 서명 키의 파일럿 프로덕션 비밀값 경계

인증·신원·세션과 ROUND 참여권의 기준은
[PRD-0005](../0005_account-and-round-authentication/spec.md)와 ADR-0017이 소유한다. 기존
공유 키 팀은 기존 접근을 유지한다. 팀별 계정 전환, 초대와 관리자·구성원·열람자 권한, 권한 이력은
[PRD-0009](../0009_team-account-access/spec.md)와 ADR-0021로 구현했다. 기존 연결을 자동 승인하지 않는다.

#### 구현 현황과 남은 작업

- `/my-teams`의 계정별 참여 팀 목록과 여러 팀 전환은 구현했다. 공개 HTTPS의 실제 기기 검증은 남아 있다.
- 결정·역할 자료의 수정·보관·복원 이력은 구현했다. 시즌·역할별 세부 권한과 다른 콘텐츠의 편집 이력은 남아 있다.
- 계정 비활성화는 모든 세션 만료·재로그인 거부·팀 권한 회수·마지막 관리자 보호·개인 CAL 구독 해지 예약을 제공한다. 조직 기록과 로그인 정보는 보존한다. 완전 탈퇴·직접 재활성화와 관리자에 의한 세션 강제 만료는 후속 범위다.
- 최근 재인증과 수명이 짧은 연결 의도를 사용하는 공급자 신원 연결·계정 병합

팀별 권한 행렬과 공유 키 종료 시점은 PRD-0009를 따른다. 공개 HTTPS의 두 기기·두 계정과 계정 팀의
격리 복원 검증은 운영 전환 전에 남아 있다.

### 7.2 여러 팀 전환과 내 업무

- 구현: 계정 권한이 승인되고 구성원 활동이 유지된 팀을 목록으로 표시한다. 현재 권한을 확인하고 기본 시즌으로 이동한다.
- 구현: 위 팀의 종료하지 않은 시즌에서 내가 맡은 미완료 반복 업무와 수락할 인수인계를 모아 본다. 기한 지난 업무·인수인계로 좁히고 원본으로 이동한다.
- 최근 활동과 초대 대기 상태
- 팀·시즌이 포함된 캐시와 URL 경계

공유 키 파일럿에서 한 팀 안의 시즌 선택·종료 시즌 탐색과 팀·시즌 URL·캐시 경계는 P1에서 구현했다. 이 단계에서는 로그인 계정을 기준으로 여러 팀을 전환하고 내 업무를 모아 본다.

### 7.3 알림·외부 연동

서비스 내 알림함은 현재 내 역할의 마감·지연 업무와 수락할 인수인계, 계정별 읽음 저장과 원본 이동을 제공한다. 계정별로 사전 알림 시간(기본 24시간, 1~168시간)과 세 가지 알림의 표시 여부를 저장하며 모든 팀·기기에 적용한다. 알림을 껐다 켜도 읽음 표시는 보존한다. 완료·보관·수락·취소·시즌 종료 시 현재 목록에서 빠진다. 외부 알림 채널과 RELAY 전달은 별도 후속 범위다.

- 실제 마감, 지연, 역할 공백과 인수인계 전달 이벤트
- 사용자 또는 역할 단위의 알림 선호
- 캘린더와 메시징·메일 채널 연동
- 중복 발송 방지, 재시도와 전달 결과 추적

관련 기능은 BATON 본체 안에 다시 만들지 않고 이미 분리한 서비스의 책임을 기준으로 연동한다.

- `BATON RELAY`는 이벤트 수신·중복 제거·전달 작업과 향후 공급자 재시도를 소유한다. BATON은 커밋된 도메인 사건만 안정적인 이벤트 ID와 버전으로 발행한다.
- `BATON WATCH`는 역할 자료 URL 스냅샷의 비동기 안전 검사와 연결 상태, 상태 변경 이벤트의 최소 1회 전달을 소유한다. BATON은 `RoleResource` 변경·시즌 종료 이후의 활성 상태를 단조 증가하는 소스 리비전으로 커밋한 뒤 동기화하고, WATCH 이벤트를 별도 인증 경계의 내구성 있는 인박스로 수신한다.
- `ROUND`는 방·피어·시그널링·TURN을 소유하고 BATON은 참여 자격을 판정해 짧은 수명의 서명된 참여권만 발급한다.
- `BATON GO`는 링크 코드·만료·폐기와 신뢰 대상 라우팅을 소유하고 BATON·ROUND의 최종 접근 권한을 대신하지 않는다.

WATCH는 자료 URL 변경을 아웃박스로 전달하고 상태 이벤트를 인박스에 저장한다. URL 대상, 시즌 종료 시 `INACTIVE`, 소스 리비전과 중복 수신 처리는 [PRD-0004](../0004_watch-integration-contract/spec.md), [ADR-0015](../../ADR/0015_watch-transactional-outbox/adr.md), [ADR-0016](../../ADR/0016_watch-health-event-transactional-inbox/adr.md)을 따른다. 공개 HTTPS에서 최초 전달·응답 유실 후 재전송과 운영 토큰 배포를 확인해야 한다. 별도 API의 현재 연결 상태 조회·재점검 화면은 구현했다. 이벤트를 누적 적용하는 상태 저장은 별도 순서·재조정 정책을 정한 뒤 추가한다.

BRIEF는 다섯 업무 점검 신호의 식별자·리비전·시간 재조정 조건과 이벤트 v2를 구현했다. 현재 고정 계약은 [`2.0.0-rc.4`](../../../contracts/brief/README.md)다. 원본 변경·자동 회차 생성과 같은 트랜잭션에서 신호와 불변 아웃박스를 저장한다. V25 송신기는 기본 비활성이며 임대·신호별 순서·결과 상태를 관리한다. 상세 규칙은 [PRD-0007](../0007_brief-continuity-signal-producer/spec.md)을 따른다.

실제 BATON·BRIEF 실행 프로세스와 MySQL·PostgreSQL을 사용한 로컬 테스트에서 재시도·동일 이벤트 재전달·심각도 변경·해소 반영·전용 Bearer·신규/직전 토큰 중첩 교체를 확인했다. 공개 HTTPS 환경의 전달·재시도·토큰 교체 검증은 남아 있다.

다른 서비스도 첫 연동 전에 서비스 인증, 커밋 후 전달, 중복 소비 방지, 재시도와 운영 지표를 PRD·ADR로 정한다. 외부 알림 채널은 계정·신원과 파일럿 요구를 확인한 뒤 선택한다.

CAL 연동은 [PRD-0006](../0006_calendar-integration-contract/spec.md)과
[ADR-0019](../../ADR/0019_calendar_snapshot_producer/adr.md)에서 불변 안정 계약 `1.0.0` 고정과 회차·마감의
손실 없는 시간 형태를 채택했다. 현재 생산자 직렬화와 원본 변경 트랜잭션의 불변 아웃박스 적재까지
구현했고 HTTP 전달·재시도와 기존 데이터 보정도 완료했다. 다음 단계는 운영 데이터 적합성
점검 후 캡처·보정·전달을 순서대로 활성화하고 실제 시즌 피드를 확인하는 것이다.

## 8. P4 — 재사용과 보조 기능

- 구현: 스터디·팀 운영의 버전이 고정된 역할·반복 업무 시작 템플릿 두 가지와 빈 구성 선택, 미리보기·응답 유실 복구. 담당자와 실제 일정은 생성 후 사용자가 정한다.
- 남은 범위: 동아리·위원회·TF별 확장과 사용자가 직접 관리하는 템플릿
- 반복 지연, 역할 공백과 인수인계 준비도 추세
- 결정과 인수인계 기록의 검색·요약 보조
- 사용자가 확인하는 초안 형태의 운영 개선 제안

AI는 조직 결정을 대신하지 않고 검색, 요약과 누락 후보 제시에만 사용한다.

## 9. 병행 기술 과제

기능 개발과 별도로 다음 구조 개선을 작은 변경으로 병행한다.

### 현재 구조

- 작업 공간 기능은 생성·접근 키·구성원·역할·반복 업무·회차·기록·인수인계별 서비스와 입력 포트로 분리했다. 명령·결과는 `WorkspaceContract`에 정의한다.
- 프런트엔드는 기능별 훅과 모달을 사용한다. 역할 상세는 브라우저 기본 대화상자를 사용하며, E2E는 공용 API 대역과 기능별 시나리오로 나눈다.
- 동시 수정·멱등 요청·트랜잭션·시간 계산은 기존 공통 정책을 사용한다. 외부 연동은 서비스별 아웃박스·인박스로 처리하며 오류 코드·요청 ID로 실패를 추적한다.
- ArchUnit으로 모듈 의존성을, REST Docs와 Gradle 작업으로 API 계약을 검증한다. 테스트 선택과 실행 순서는 [ADR-0002](../../ADR/0002_test-strategy/adr.md)를 따른다.

세부 변경 이력은 Git에서 확인한다. 현재 모듈·패키지 기준은 [ADR-0001](../../ADR/0001_hexagonal-architecture/adr.md)을 따른다.

### 남은 구조 개선

- WATCH 공개 HTTPS에서 상태 조회·재점검과 콜백·응답 유실 뒤 재전송·적체 해소를 검증한다. 자료 연결 상태 조회는 기존 워크스페이스 조회와 분리한다.
- WATCH 인박스 처리 상태와 보존, 이벤트 순서·현재 상태 조정 정책 채택
- WATCH 독립 DB 복구 때 소스 리비전 재기준화 절차 보강
- 나머지 대형 워크스페이스 UI와 모달을 기능 소유 단위로 분리
- 유스케이스·REST Docs 대형 테스트를 기능 경계로 분리
- 데이터가 늘기 전 워크스페이스 프로젝션의 조건부 조회, 페이지네이션 또는 갱신 방식 재검토

구조 분리는 동작 변경과 섞지 않고 각 기능을 추가하기 직전의 가장 가까운 경계부터 수행한다.

## 10. 당장 개발하지 않는 범위

- BATON 본체 안의 자체 채팅과 화상회의. 영상·음성·휘발성 채팅은 별도 ROUND 서비스가 소유한다.
- 범용 문서 편집기와 파일 저장소
- 출석, 회계, 급여, 평가와 학사 행정 전체
- 복잡한 전자결재
- 모든 프로젝트 관리 기능
- AI의 자동 의사결정

실제 파일럿에서 BATON의 핵심 흐름과 직접 연결된 요구가 확인되기 전에는 이 범위를 확장하지 않는다.

## 11. 실행 순서

현재 기준의 권장 실행 순서는 다음과 같다.

1. 실제 공개 URL의 외부 상태 감시와 알림 수신, 암호화 원격 백업의 별도 환경 복구, 실제 OAuth·SMTP·ROUND·CAL·WATCH 자격 증명과 공개 HTTPS를 사용하는 남은 P0 운영 검증
2. 반복 업무 정의 보관을 포함한 실제 그룹 스터디 반복 운영 검증
3. 공개 스테이징의 WATCH→BATON 상태 변경 이벤트 전달·재전송과 운영 활성화 검증
4. BATON–WATCH 현재 상태 조회·재점검의 파일럿 URL 검증과 독립 복원 절차 확인
5. 결정 Markdown의 파일럿 사용을 확인한 뒤 역할 목적·반복 업무 상세로 확대
6. 업무 점검과 결정·인수인계·자료 검색의 파일럿 실사용 검증
7. 계정 권한의 운영 전환 검증과 다중 팀 탐색
8. BATON 참여권을 사용하는 ROUND와 정책 링크를 사용하는 BATON GO 연동
9. BRIEF 공개 HTTPS의 전달·재시도·조회·생성·토큰 교체 검증
10. BATON RELAY 공급자 전달이 준비된 뒤 알림 이벤트 연동
11. 템플릿·분석·AI 보조

각 단계는 사용자 흐름, 실패 경계, 데이터 보존 규칙과 완료 기준을 별도 요구사항으로 확정한 뒤 API 계약과 함께 구현한다.
