# PRD-0001: BATON 제품 기준선

- 상태: 초기 기준선
- 작성일: 2026-07-20
- 대상: 웹 서비스 MVP와 실제 그룹 스터디 파일럿

## 1. 제품 정의

BATON은 사람이 바뀌어도 역할과 운영의 기억이 이어지게 하는 조직 운영 OS다.

스터디, 동아리, 학생회, 학교 위원회, 회사의 프로젝트 팀과 TF처럼 여러 사람이 반복해서 함께 일하는 조직을 대상으로 한다. 사람 명단이나 할 일만 관리하지 않고, 역할의 목적과 책임, 반복 운영, 결정의 이유, 인수인계에 필요한 맥락을 하나의 흐름으로 연결한다.

## 2. 해결하려는 문제

작은 조직은 별도의 운영 시스템 없이 메신저, 문서, 캘린더와 개인 기억에 의존하기 쉽다. 이때 다음 문제가 반복된다.

- 해야 할 일이 특정 사람의 기억에 붙어 있어 담당자가 바뀌면 빠진다.
- 반복 업무의 순서와 기준이 매번 다시 논의된다.
- 결정 결과만 남고 이유와 검토했던 대안은 사라진다.
- 인수인계가 임기나 프로젝트 종료 직전에 한꺼번에 이루어진다.
- 누가 떠날 때 끊길 지식과 권한을 미리 발견하기 어렵다.

BATON은 이를 `역할`, `운영 리듬`, `조직의 기억`, `바통`이라는 네 축으로 다룬다.

## 3. 제품 원칙

### 역할이 사람보다 오래 남는다

책임은 사람에게 직접 고정하지 않고 역할에 둔다. 사람은 정해진 기간 동안 역할을 맡는다. 담당자가 바뀌어도 역할의 목적, 책임, 기록은 유지되어야 한다.

### 운영은 반복 가능한 리듬으로 보인다

한 번의 할 일뿐 아니라 모임 전·중·후, 매주, 매월처럼 되풀이되는 운영을 한눈에 확인할 수 있어야 한다.

### 결과와 함께 이유를 남긴다

결정에는 무엇을 정했는지뿐 아니라 이유, 검토한 대안, 영향을 받는 역할을 함께 남긴다.

### 인수인계는 마지막 날의 문서 작업이 아니다

역할을 수행하는 동안 책임, 루틴, 결정, 자료와 위험 신호가 계속 쌓이고, 필요할 때 바통북으로 정리되어야 한다.

### 스터디에서 시작해 더 큰 조직으로 확장한다

첫 실제 사용처는 사용자가 참여하는 그룹 스터디다. 다만 제품 모델은 학교와 회사에도 적용할 수 있도록 조직 종류에 종속되지 않는 용어와 경계를 사용한다.

## 4. 핵심 개념

| 개념 | 의미 |
| --- | --- |
| 팀 | 지속적으로 운영 기록을 소유하는 기본 공간. 스터디, 동아리, 위원회, 회사 팀 등을 모두 포함한다. |
| 시즌 | 학기, 기수, 프로젝트처럼 시작과 종료가 있는 운영 기간이다. |
| 구성원 | 팀에 참여하는 사람이다. 역할과 동일하지 않다. |
| 역할 | 사람과 분리해 유지하는 목적과 책임의 묶음이다. |
| 역할 배정 | 구성원이 특정 기간 동안 역할을 맡는 관계다. |
| 운영 루틴 | 특정 역할이 반복 수행할 일의 이름, 단계, 기한 문구와 실행 방법을 담은 정의다. |
| 운영 회차 | 시즌 안에서 사용자가 이름과 모임 날짜를 정해 만드는 한 번의 운영 단위다. 운영 중 메타데이터를 정정하고 실행 기록을 지우지 않은 채 보관·복원할 수 있다. |
| 루틴 실행 | 회차를 만들 때 존재한 루틴 정의를 복사한 회차별 실행 기록이다. 완료 상태는 다른 회차와 독립적이다. |
| 결정 기록 | 결정 내용, 이유, 검토한 대안, 작성자와 관련 역할을 담는 조직의 기억이다. |
| 자료 | 역할 수행과 인수인계에 필요한 문서나 외부 링크다. |
| 위험 신호 | 담당자 부재, 개인에게만 있는 지식, 지연된 반복 업무처럼 기억 단절 가능성을 보여주는 단서다. |
| 바통북 | 역할의 목적·책임·루틴·결정·자료·위험과 남은 정리를 모은 인수인계 묶음이다. |

이 표는 제품 언어의 기준선이다. 데이터베이스 테이블, 상태 enum, 세부 제약을 확정하는 문서는 아니다.

## 5. 핵심 사용자 경험

### 오늘

사용자는 현재 시즌에서 지금 확인하거나 수행해야 할 역할별 루틴, 지연과 인수인계 위험을 본다.

### 역할

팀이 지속해서 필요로 하는 역할을 만들고 목적, 책임, 현재 담당 기간과 다음 담당자를 확인한다.

### 운영

모임 또는 업무의 전·중·후에 반복되는 루틴을 역할과 연결하고 이번 회차의 진행 상황을 확인한다. 잘못 입력한 회차 이름·날짜는 실행 기록을 유지한 채 정정하고, 현재 운영에서 치울 회차는 보관했다가 복원한다.

### 기록

중요한 결정을 이유와 대안까지 기록하고 관련 역할에서 다시 찾는다. 잘못 입력한 기록은 정정하고, 당장 사용하지 않는 기록은 삭제하지 않고 보관했다가 복원한다.

### 바통

역할별 인수인계 준비 상태를 확인하고 책임, 루틴, 결정, 자료, 조언과 남은 작업을 바통북으로 정리한다. 바통 항목도 운영 중 정정하고 보관·복원할 수 있다.

## 6. MVP 범위

- 팀과 기간이 있는 시즌을 만든다.
- 구성원과 역할을 분리해 관리하고 역할 담당 기간을 기록한다.
- 역할의 목적, 책임과 반복 루틴을 관리한다.
- 이번 운영 회차의 완료 여부와 지연을 확인한다.
- 결정 내용, 이유, 대안과 관련 역할을 기록한다.
- 역할에 자료와 위험 신호를 연결한다.
- 역할별 바통북을 준비하고 다음 담당자에게 전달할 내용을 확인한다.
- 스터디를 모바일과 데스크톱 웹에서 실제 운영할 수 있다.

세부 상태값, 알림 시점, 권한 행렬과 보존 기간은 실제 파일럿에서 필요한 흐름이 확인된 뒤 별도 결정한다.

### 첫 파일럿 구현 단위

첫 그룹 스터디 파일럿은 전체 MVP 중 다음 세로 흐름을 먼저 사용한다.

- 온보딩에서 한 팀, 한 시즌과 중복되지 않는 이름의 초기 구성원을 함께 만든다. 이름이 같은 사람은 구분 가능한 별칭을 사용한다.
- 워크스페이스 공유 링크를 받은 구성원은 같은 서버 데이터를 읽고 쓴다. 열린 화면은 전경에서 10초마다 최신 워크스페이스를 확인하고, 창으로 돌아오거나 네트워크가 복구되면 즉시 다시 조회한다.
- 역할의 이름, 목적, 담당자, 담당 기간, 책임과 위험 신호를 만들고 운영 중 수정한다.
- 역할에 문서나 외부 자료 링크를 연결하고 제목, URL, 설명과 소유 역할을 운영 중 수정한다.
- 시즌의 반복 루틴 정의를 만들고 수정한다. 이름과 시즌 안의 모임 날짜를 지정해 회차를 수동 생성하고, 생성 시 복사된 루틴 실행을 회차별로 완료 처리한다. 회차 이름·날짜를 정정하거나 회차를 보관·복원해도 실행 식별자, 스냅샷과 완료 상태는 유지한다.
- 결정 내용, 이유, 대안, 작성자와 관련 역할을 기록하고 운영 중 정정한다. 당장 사용하지 않는 결정은 보관함으로 옮겼다가 복원한다.
- 역할별 바통 항목을 만들고 내용·분류·소유 역할과 준비 여부를 갱신한다. 당장 사용하지 않는 항목은 보관함으로 옮겼다가 복원한다.
- 제품 데이터는 MySQL을 단일 기준으로 사용하고 브라우저 `localStorage`와 이중 저장하지 않는다.
- 응답이 유실된 온보딩 재시도는 같은 워크스페이스로 복구되고 중복 팀을 만들지 않는다.
- 역할·루틴·회차·결정·바통 항목·역할 자료 생성 응답이 유실되어도 같은 요청을 재시도해 이미 생성된 항목을 되찾고 중복 기록을 만들지 않는다.
- 접근 키 회전·복구 응답이 유실되어도 같은 멱등 요청으로 이미 발급된 키를 회수한다. 더 최신 키 변경 뒤 과거 멱등 키를 재사용해 폐기된 링크를 되살릴 수는 없다.
- 브라우저는 워크스페이스·콘텐츠 생성과 키 회전 멱등 정보를 내구 저장하고 다시 읽어 확인한 뒤 요청한다. 저장소가 차단되면 응답 유실을 안전하게 복구할 수 없으므로 요청을 시작하지 않는다.
- 검증된 워크스페이스는 이 브라우저의 최근 목록에서 다시 열 수 있고, 잘못된 공유 키가 기존 정상 키를 덮어쓰지 않는다.
- 유출된 공유 키를 회전하고, 모든 구성원이 키를 잃으면 생성 권한과 분리된 파일럿 복구 키로 새 키를 복구한다.

공유 링크에는 워크스페이스 접근 키가 URL fragment로 포함된다. 서버는 원문 접근 키와 워크스페이스·콘텐츠 생성 및 키 변경 멱등 키를 저장하지 않고 SHA-256 기반 해시만 저장한다. 접근 키 원문은 최초 성공 응답과 동일 멱등 요청의 응답 유실 복구 때만 반환된다. 이 방식은 계정·초대·세부 권한 모델이 정해지기 전 파일럿에만 적용하며, 링크를 아는 사람은 해당 워크스페이스를 읽고 쓸 수 있다.

다음 항목은 첫 파일럿 구현 단위에 포함하지 않는다.

- 회차 자동 생성, 실제 마감 시각과 지연 자동 판정
- 구성원·시즌의 수정과 모든 제품 기록의 영구 삭제
- 여러 팀·시즌을 한 계정에서 선택하는 화면
- 계정, 초대, 역할별 세부 권한과 감사 이력

## 7. 현재 구현 상태

현재 프런트엔드는 실제 파일럿 온보딩과 서버 저장 워크스페이스를 제공한다.

- 팀, 시즌 기간과 초기 구성원을 등록하고 공유 링크를 만든다.
- 오늘, 역할, 운영, 기록, 바통 화면을 서버 projection으로 표시한다.
- 역할과 루틴 정의를 만들고 수정하며, 역할별 자료 링크를 만들고 수정한다. 수동 회차를 만들고 이름·모임 날짜를 정정하며, 선택한 활성 회차의 루틴 실행을 완료 처리한다. 회차·결정·바통 항목은 가역적으로 보관·복원하고, 결정·바통 내용과 바통 완료 상태도 갱신한다.
- 워크스페이스 projection은 회차·결정·바통의 활성 기록과 보관 기록을 함께 반환한다. 프런트엔드는 `archivedAt`이 없는 기록을 일반 화면에, 값이 있는 기록을 보관함에 나누어 표시해 새 조회 API 없이 복원할 수 있게 한다. 보관된 회차는 수정하거나 실행 완료 상태를 바꿀 수 없고 복원한 뒤 다시 운영한다.
- 열린 워크스페이스는 전경에서 10초마다 자동 동기화하고 창 포커스·네트워크 복구 시 다시 조회한다. 마지막 화면 갱신 시각과 수동 새로고침을 제공하며, 일시적인 재조회가 실패하면 기존 내용을 유지한 채 동기화 실패를 알린다. 접근 키가 폐기된 `403`은 기존 내용을 계속 편집할 수 있는 것처럼 표시하지 않고 접근 오류 화면으로 전환한다.
- 공유 콘텐츠 변경에서 `409 WORKSPACE_CONTENT_CONFLICT`를 받으면 열려 있던 편집 입력을 폐기하고 최신 workspace projection을 다시 조회한다. 이 조회가 진행 중이거나 실패한 동안에는 기존 기록의 수정·보관·완료 변경을 막고 수동 재시도를 제공하며, 조회 성공 뒤 최신 화면에서 사용자가 변경 의도를 다시 선택하게 한다.
- 로딩, 오류, 빈 상태, 중복 제출 방지와 모바일 레이아웃을 제공한다.
- 서버 검증이 끝난 접근 키만 저장하고, 최근 워크스페이스 최대 5개를 다시 열거나 목록에서 지울 수 있다.
- 제품 데이터는 브라우저 `localStorage`에 저장하지 않는다. 로컬에는 접근 키, 최근 목록용 이름·식별자·시각과 완료 전 워크스페이스·콘텐츠 생성 및 키 회전 요청의 멱등 정보만 보관한다. 워크스페이스 생성은 정규화된 요청별로 최대 5개, 역할·루틴·회차·결정·바통·역할 자료 콘텐츠 생성은 모든 작업 공간의 미완료 요청을 합쳐 최대 20개까지 작업 공간과 작업 종류별로 구분해 보관한다.
- 콘텐츠 생성과 키 관리 화면의 접근 키 회전은 완료 전 멱등 정보를 내구 저장할 수 없으면 요청을 차단한다. 서버 반영 뒤 응답만 유실되면 저장한 동일 멱등 요청으로 생성된 리소스나 새 키를 회수한다.

백엔드는 팀·시즌·구성원·역할·역할 자료·루틴 정의·운영 회차·루틴 실행·결정·바통 항목의 MySQL 영속 모델, Flyway migration과 `/api/v1` 파일럿 계약을 제공한다. application 경계에서 공유 키, 워크스페이스·콘텐츠 생성과 키 변경의 멱등성, 역할·자료·루틴·회차·실행·결정·바통의 소속과 불변식, 분리된 생성 게이트와 운영자 복구 권한을 검증한다. 자료 URL은 사용자 정보가 없는 `http` 또는 `https` 전체 주소만 허용하고 서버가 링크 대상을 조회하거나 신뢰성을 판정하지 않는다. 회차 생성은 현재 루틴 정의 전체를 실행 기록으로 한 번만 복사하며, 이후 추가하거나 수정한 루틴은 이미 만든 회차를 바꾸지 않고 다음 회차부터 반영된다. 회차 이름·날짜 수정과 보관·복원은 기존 실행 식별자·스냅샷·상태를 바꾸지 않으며, 보관된 회차 이름도 시즌 안에서 계속 예약된다. 콘텐츠 생성은 멱등 예약과 리소스 저장을 한 트랜잭션으로 처리하고, 접근 키 변경과 역할·역할 자료·루틴 정의·시즌 회차·회차 실행·결정·바통의 겹친 수정은 낙관적 잠금으로 조용한 덮어쓰기를 막는다. 회차 보관과 실행 완료는 회차 행의 잠금을 공유해 보관된 회차에 완료 변경이 뒤늦게 반영되지 않게 한다. 회차·결정·바통의 보관은 UTC `archivedAt`을 기록하는 가역 상태 변경이며 영구 삭제가 아니다. 기존 `routines.status`는 `회차 도입 이전 기록` 회차의 실행 상태로 이관하며 실제 과거 날짜를 알 수 없어 해당 회차의 날짜는 운영자가 실제 날짜로 정정할 때까지 비어 있다. 프로덕션 파일럿은 동일 출처 HTTPS와 내부 전용 MySQL, 백업·복구 스크립트를 제공한다. 최종 계정·인증과 다중 시즌 탐색은 아직 구현하지 않았다.

## 8. 첫 파일럿

사용자가 참여하는 그룹 스터디를 첫 운영 현장으로 삼는다.

- 실제 스터디의 시즌과 역할을 등록한다.
- 공유 링크를 파일럿 구성원에게 전달하고 같은 기록이 각 브라우저에서 보이는지 확인한다.
- 실제 HTTPS 주소를 서로 다른 두 기기에서 열어 공유 링크와 변경 동기화를 확인한다.
- 매 회차 전·중·후 루틴을 BATON에서 확인한다.
- 운영 방식이 바뀔 때 이유와 대안을 남긴다.
- 역할 교대 전에 바통북을 실제 다음 담당자가 읽고 보완한다.
- 별도 설명 없이도 다음 행동을 찾을 수 있는지 관찰한다.
- 실제 기록을 넣기 전에 백업을 만들고 별도 환경에서 한 번 복구한다.

파일럿에서는 기능 수보다 다음 신호를 우선 확인한다.

- 담당자가 없어 빠지는 책임을 더 일찍 발견하는가
- 반복 운영을 준비하는 시간이 줄어드는가
- 과거 결정의 이유를 다시 찾을 수 있는가
- 다음 담당자가 질문해야 하는 양과 시행착오가 줄어드는가

## 9. 초기 비목표

- 메신저나 화상 회의를 대체하는 자체 채팅
- 급여, 인사평가, 성적과 학사 행정 전체를 다루는 ERP
- 범용 문서 편집기나 파일 저장소 대체
- 복잡한 전자결재와 회계
- 모든 프로젝트 관리 기능을 한 번에 제공하는 것
- AI가 사람을 대신해 조직의 결정을 내리는 것

외부 문서, 캘린더와 메시징 연동은 핵심 흐름이 검증된 뒤 검토한다.

## 10. 미결정 사항

다음 항목은 이 기준선에서 확정하지 않는다.

- 회원가입, 소셜 로그인, 초대와 세션을 포함한 인증 방식
- 팀·시즌·역할별 세부 권한 모델
- 파일럿 이후의 클라우드 공급자, 다중 호스트와 무중단 배포 방식
- 알림 채널과 외부 서비스 연동
- 과금 방식
- 결정·바통 이외 도메인의 세부 상태 머신과 영구 삭제·보존 기간 정책

현재 백엔드의 HTTP Basic 설정은 개발 기반을 위한 임시 보호 장치이며 최종 인증 결정이 아니다.
파일럿 공유 키 역시 최종 계정·권한 모델이 아니라 한정된 그룹에서 핵심 흐름을 검증하기 위한 임시 접근 방식이다.
