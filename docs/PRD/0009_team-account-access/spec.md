# PRD-0009: 팀 초대와 계정별 접근 권한

- 상태: 채택
- 결정일: 2026-09-05
- 대상: 기존 공유 키 팀의 선택적 계정 전환, 구성원 초대와 권한 관리

## 1. 팀별 전환

새 팀과 기존 팀은 기본적으로 공유 키 방식을 유지한다. 로그인 자체로 팀 접근 권한을 얻지 않는다.
운영자는 본인 계정을 활동 중인 기존 구성원과 연결한 뒤 구성원 관리의 `팀 초대·권한 관리`에서
운영자 복구 키를 입력하고 공유 링크 접근 종료를 확인한다. 서버는 해당 계정을 첫 관리자로 지정하고
`accountAccessEnabled=true`로 전환한다. 다른 기존 계정 연결은 승인되지 않은 상태로 남는다.

전환된 팀에서는 모든 시즌의 기존 공유 키와 직접 구성원 연결 요청을 거부한다. 초대받은 계정은
공유 키 없이 팀·시즌 주소로 접근한다. 다시 공유 키 방식으로 되돌리는 API는 제공하지 않는다.
WATCH·CAL·BRIEF의 서비스 전용 인증은 팀 권한으로 대체하지 않는다.

## 2. 권한

권한은 팀 전체에 적용하며 활동 중인 구성원과 연결되어야 한다. `null`은 접근 취소 또는 승인 전이다.

| 동작 | 열람자 `VIEWER` | 구성원 `MEMBER` | 관리자 `ADMIN` |
| --- | --- | --- | --- |
| 시즌·역할·운영·기록·인수인계와 자료 확인 이력 조회 | 허용 | 허용 | 허용 |
| 자료 연결 상태 조회 | 허용 | 허용 | 허용 |
| 자료 URL 재점검 접수 | 거부 | 허용 | 허용 |
| 내 업무·알림 조회와 내 알림 읽음 | 허용 | 허용 | 허용 |
| 열린 시즌의 개인 캘린더 구독 발급·재발급 | 허용 | 허용 | 허용 |
| 역할·반복 업무·회차·결정·인수인계 항목·자료 변경과 자료 확인 기록 | 거부 | 허용 | 허용 |
| 본인 명의의 인수인계 전달·수락·취소 | 거부 | 담당자 조건 충족 시 허용 | 담당자 조건 충족 시 허용 |
| 구성원 추가·이름·활동 상태 변경 | 거부 | 거부 | 허용 |
| 시즌 이름·기간·자동 일정 설정, 종료·재개·다음 시즌 생성 | 거부 | 거부 | 허용 |
| 초대 생성·취소와 구성원 권한 변경·권한 이력 조회 | 거부 | 거부 | 허용 |

종료 시즌의 일반 변경 금지는 모든 권한에 동일하게 적용한다. 인수인계의 `confirmedByMemberId`는
계정 전환 팀에서 로그인 계정과 연결된 구성원이어야 하며 기존 이전·다음 담당자 조건도 적용한다.
공유 키 팀의 과거 확인 기록을 로그인 신원을 확인한 기록으로 바꾸지 않는다.

권한을 회수하거나 구성원이 활동 종료하면 이후 작업 공간 접근과 새 ROUND 참여권 발급을 거부한다.
CAL 구독은 같은 권한 회수 트랜잭션에 폐기 요청을 남기며 CAL 전달이 끝나면 기존 주소를 차단한다.
팀 전환 시 승인 전 계정의 기존 구독도 폐기하고, 권한 재승인은 이전 폐기를 취소하지 않는다.
본인 구독의 상태 조회·해지는 팀 접근 권한 회수 후에도 가능하다. 상세 정책은 [PRD-0006](../0006_calendar-integration-contract/spec.md)을 따른다.
이미 발급한 ROUND 참여권은 기존 짧은 만료 정책을 따른다. 열람자도 ROUND 참여는 가능하며 방 매핑
변경은 일반 변경 권한이 필요하다. 마지막 활성 관리자는 강등·접근 취소·활동 종료할 수 없다.

## 3. 초대

관리자는 먼저 팀 구성원을 등록한 뒤 해당 구성원과 권한을 지정해 7일짜리 링크를 만든다.
같은 구성원의 이전 미수락 초대는 취소된다. 이미 승인된 계정은 초대 대신 권한 변경을 사용한다.

- 초대 토큰은 32바이트 난수의 43자 Base64 URL 표현이며 DB에는 용도를 구분한 SHA-256 해시만 저장한다.
- 원문은 생성 응답에서만 제공한다. 관리자 화면을 닫으면 원문을 다시 조회할 수 없다.
- 링크는 `/join#invite=...`다. 토큰을 로그인 복귀 쿼리에 넣지 않는다.
- 초대 화면은 같은 탭의 로그인 복귀를 위해 토큰을 `sessionStorage`에 보관하고 주소 프래그먼트를 제거한다.
  저장을 못 하면 로그인 후 원래 링크를 다시 열도록 안내한다. 수락하면 보관한 토큰을 제거한다.
- 로그인 후 팀 이름·구성원 이름·권한을 확인하고 명시적으로 수락한다. 링크 열기만으로 수락하지 않는다.
- 수락 시 계정 연결, 권한 부여와 초대 소비를 같은 트랜잭션에서 처리한다. 다른 계정이나 구성원과
  이미 연결되어 있으면 `409 ACCOUNT_MEMBERSHIP_CONFLICT`다.
- 만료 시각과 같은 시각부터 만료다. 취소·만료 초대는 수락할 수 없다.
- 응답 유실 후에는 같은 계정만 재확인·재수락할 수 있다. 현재 권한을 반환하며 회수된 권한을 복원하지 않는다.
- 권한 변경 시 해당 구성원의 미수락 초대도 취소한다.

초대의 전달은 관리자가 직접 한다. 이메일 발송과 탈퇴·계정 병합은 이 범위에 없다. 계정별 참여 팀 목록은 아래 계약을 따른다.

## 4. 계정과 요청 확인

계정은 기존 서버 세션으로 확인한다. 계정이 있는 모든 작업 공간 변경 요청에 CSRF와 동일 출처를
요구한다. 일반 작업 공간 변경에는 화면이 확인한 `X-Baton-Account-Id`도 보내며, 초대·권한과
기존 개인 기능은 요청 본문의 `expectedAccountId`를 검사한다. 계정이 바뀌면 이전 계정의 작업 공간
캐시를 취소·제거하고 화면을 다시 만든다. 조회 키에도 계정 ID를 포함한다.

공유 키만 사용하는 비로그인 요청은 기존 계약을 유지한다. 공유 키가 있어도 로그인 세션을 함께
사용하는 변경 요청에서 CSRF를 생략할 수 없다.

## 5. 권한 이력과 관리자 복구

관리자 지정·복구, 초대 생성·취소·수락과 권한 변경에 대해 계정·대상 구성원·이전/새 권한·서버 시각을
저장하고 최근 50건을 표시한다. 업무 기록 전체의 편집 감사 이력을 뜻하지 않는다.

관리자 접근을 잃었을 때 운영자는 복구 키와 해당 팀의 활성 구성원에 이미 연결된 계정으로
`POST /api/v1/team-access/{teamId}/activate`를 호출해 관리자를 복구한다. 이 과정도 이력에 남긴다.
복구 키만으로 새로운 계정·구성원 연결을 만들거나 로그인 검사를 생략할 수 없다.

백업에는 스냅샷 이후 회수된 권한과 취소된 초대가 남아 있을 수 있다. `ops/restore.sh`는 DB를
불러온 뒤 계정 권한 팀이 있으면 성공 처리와 공유 키 복구 대상 생성을 중단하고 서버를 정지한
상태로 둔다. 계정 권한·초대를 자동 폐기하지 않는다. 공개 전에 격리된 환경에서 현재 권한·초대와
스냅샷을 대조하는 별도 운영 복구 검증이 필요하며, 계정 팀의 자동 복원 완료는 지원하지 않는다.

## 6. 검증과 운영 적용

자동 검증은 실제 MySQL의 전환·초대·권한 규칙, HTTP 보안 필터, 브라우저별 초대 수락·편집 제한과
복원 스크립트의 완료 중단 경계를 다룬다. 실제 공개 HTTPS의 두 계정·두 기기, 운영 복구 키 전달과
계정 권한 팀의 격리 복원은 운영자가 전환 전에 검증해야 한다. 기존 팀을 자동 전환하지 않는다.

## 내 팀 목록과 팀 전환

- `/my-teams`는 로그인 계정이 승인된 활성 구성원인 계정 권한 팀을 서버에서 조회한다. 공유 키 팀,
  미승인·권한 회수·활동 종료 구성원은 제외한다. 목록에는 팀 이름·본인 이름·현재 권한과 이동할 시즌을 표시한다.
- 팀 이름·식별자 순으로 정렬한다. 종료되지 않은 시즌을 우선하고, 모두 종료됐으면 시작일·식별자 내림차순의
  첫 시즌으로 이동한다. 실제 작업 공간은 이동 시 현재 권한을 다시 확인한다.
- 시작 화면·로그인 완료 화면·작업 공간에서 내 팀으로 이동한다. 새 기기에서도 같은 목록을 조회하며
  공유 키를 가져오거나 발급하지 않는다. 공유 키 팀의 최근 방문 목록은 기기 범위로 유지한다.
- 목록은 30초마다 전경에서 갱신하고 창 포커스·수동 새로고침 때 다시 확인한다. 계정 전환 시 이전 목록을 제거한다.

## 계정 비활성화와 관리자 유지

계정 비활성화 시 승인된 팀 권한을 회수하고 `ACCOUNT_DEACTIVATED` 이력을 남긴다. 어느 계정 권한 팀에서든 마지막 활성 관리자이면 다른 관리자를 지정할 때까지 전체 요청을 거부한다. 비활성 계정에 초대·운영자 복구·직접 권한 변경으로 새 권한을 부여하지 않는다. 구성원·조직 기록과 공유 키 팀의 공유 키는 보존한다.
