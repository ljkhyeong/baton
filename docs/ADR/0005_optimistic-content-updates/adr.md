# ADR-0005: 공유 콘텐츠의 겹친 수정을 낙관적 잠금으로 거절

- 상태: 채택. 루틴 완료 상태의 소유권은 ADR-0006으로 대체
- 결정일: 2026-07-21

## 배경

BATON 파일럿은 공유 링크를 받은 여러 구성원이 같은 역할, 역할 자료, 루틴 정의, 회차별 루틴 실행, 결정 또는 바통 항목을 수정한다. 두 트랜잭션이 같은 행을 먼저 읽고 차례로 커밋하면 Hibernate의 늦은 UPDATE가 먼저 반영된 값을 조용히 되돌릴 수 있다. 최초 결정 당시에는 루틴 정의와 완료 상태가 한 `Routine` 행에 있었지만, ADR-0006 이후 완료 상태는 회차별 `RoutineExecution`이 소유한다. ADR-0007에서 결정과 바통의 내용 수정·보관·복원도 같은 공유 콘텐츠 변경 경계에 들어왔다.

## 결정

- `Role`, `RoleResource`, 루틴 정의인 `Routine`, 회차별 `RoutineExecution`, `Decision`과 `HandoffItem`에 JPA `@Version` 값을 둔다. Flyway는 기존 행의 버전을 `0`으로 초기화하고 새 행도 `0`에서 시작한다.
- 역할·역할 자료·루틴 정의·루틴 실행·결정·바통 저장은 transaction 종료 전에 flush해 낙관적 잠금 충돌을 persistence adapter 경계에서 확인한다.
- 겹친 수정 중 늦게 커밋한 요청은 `409 WORKSPACE_CONTENT_CONFLICT`로 수렴한다.
- 프런트는 충돌 뒤 workspace projection을 다시 조회하고, 사용자가 최신 상태를 확인한 뒤 수정 내용을 다시 제출하게 한다.
- 버전은 현재 HTTP DTO에 노출하지 않는다. 첫 파일럿에서는 실제로 겹친 DB 트랜잭션의 무응답 덮어쓰기를 막는 최소 경계만 채택한다.

## 결과

### 장점

- 같은 역할, 역할 자료, 루틴 정의, 회차 실행, 결정 또는 바통 항목을 수정하는 요청이 동시에 커밋될 때 한 요청이 다른 요청의 값을 조용히 지우지 않는다.
- 루틴 정의와 회차 실행은 서로 다른 행이므로 정의 수정과 완료 처리는 충돌하지 않고 각자의 값을 보존한다.
- 결정과 바통의 내용 수정·완료·보관·복원이 같은 행의 현재 상태를 놓고 경쟁하면 늦은 요청이 충돌로 드러난다.
- HTTP 요청·응답에 저장소 버전을 노출하지 않고도 가장 위험한 겹친 transaction을 감지한다.
- MySQL 통합 테스트에서 실제 JPA flush와 충돌 변환을 검증할 수 있다.

### 비용과 한계

- 충돌한 사용자는 최신 projection을 확인하고 수정 내용을 다시 입력하거나 제출해야 한다.
- 두 요청이 DB에서 겹치지 않고 순서대로 도착하면 오래 열린 브라우저의 전체 편집 값이 앞선 변경을 덮을 수 있다. 파일럿에서 이 문제가 관찰되면 버전을 응답에 노출하고 `If-Match` 또는 동등한 사전 조건을 추가한다.
- version column과 충돌 예외 변환을 역할·역할 자료·루틴 정의·루틴 실행·결정·바통의 모든 저장 경로에서 유지해야 한다.

## 대안

### 마지막 저장 우선

구현은 단순하지만 공동 사용에서 데이터가 사라져도 사용자가 알 수 없어 채택하지 않았다.

### 처음부터 ETag 또는 요청 version 적용

오래 열린 클라이언트까지 보호하지만 모든 DTO, mutation과 캐시 정책을 함께 확장해야 한다. 첫 파일럿에서는 실제 요구가 확인될 때까지 보류한다.

## 검증

```bash
./gradlew --no-daemon :application:useCaseTest
./gradlew --no-daemon build
```

MySQL에서 같은 역할, 역할 자료, 루틴 정의, 루틴 실행, 결정 또는 바통 항목을 먼저 읽은 두 트랜잭션 중 하나만 저장되고, 다른 요청이 `WORKSPACE_CONTENT_CONFLICT`로 변환되는지 확인한다. 루틴 정의 수정과 별도 실행 완료 처리는 서로를 덮어쓰지 않는지도 확인한다.
