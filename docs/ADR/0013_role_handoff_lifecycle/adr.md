# ADR-0013: 역할 인수인계 전달을 별도 생명주기와 역할 잠금으로 관리

- 상태: 채택
- 결정일: 2026-07-30

## 배경

BATON의 기존 인수인계 문서는 역할별 준비 항목과 자료를 계속 쌓는 기능은 제공했지만, 실제 역할 교대가 언제 준비되고 누가 전달·수락했으며 어느 담당 기간으로 바뀌었는지는 기록하지 않았다. 운영자가 역할의 `currentMemberId`, `nextMemberId`와 담당 기간을 직접 수정하면 준비 중인 교대와 완료한 과거 교대를 구분할 수 없고, 전달 직후 인수인계 항목이나 자료가 바뀌어 다음 담당자가 확인한 범위가 달라질 수도 있다.

작은 그룹 스터디 파일럿에서는 계정 인증 없이 공유 접근 키를 사용한다. 따라서 이전·다음 담당자의 명시적인 확인은 필요하지만, 요청에 담긴 구성원 ID를 실제 로그인 신원이나 법적 서명으로 과장해서는 안 된다.

시즌 종료와 다음 시즌 시작도 열린 역할 교대와 충돌한다. 준비·전달 중인 인수인계를 둔 채 시즌을 종료하거나 역할 스냅샷을 새 시즌으로 복사하면 어느 시즌에서 교대를 끝내야 하는지 모호해진다.

## 결정

### 별도 역할 인수인계 애그리거트

- 역할 교대 이력은 `Role` 필드만 덮어쓰지 않고 별도 `RoleHandoff` 애그리거트로 보존한다.
- 한 이력은 역할, 이전·다음 담당자, 준비 시점의 이전 담당 기간과 수락 뒤 적용할 다음 담당 기간을 소유한다.
- 역할마다 열린 `PREPARING` 또는 `TRANSFERRED` 이력은 하나만 허용한다. 완료한 `ACCEPTED`와 `CANCELLED` 이력은 삭제하지 않는다.
- 워크스페이스 프로젝션은 역할별 전체 역할 인수인계 이력을 반환한다.

### 상태와 전환

```text
PREPARING ──전달──> TRANSFERRED ──수락──> ACCEPTED
    │                    │
    └──────취소──────────┴──────────────> CANCELLED
```

- 준비는 현재 담당자와 현재 담당 시작일이 있는 역할에서만 시작한다. 현재·다음 담당자는 서로 다른 활동 중 팀 구성원이어야 한다.
- 준비할 때 역할의 `nextMemberId`를 다음 담당자로 맞추고 두 담당자, 이전 담당 기간과 요청한 다음 담당 기간을 `RoleHandoff`에 고정한다.
- 전달은 준비 당시 이전 담당자 ID를 확인자로 선언해야 한다.
- 수락은 준비 당시 다음 담당자 ID를 확인자로 선언해야 한다. 수락 트랜잭션은 역할의 현재 담당자를 다음 담당자로 바꾸고 `nextMemberId`를 비우며, 담당 기간을 준비 때 고정한 다음 담당 기간으로 바꾼다.
- 취소는 `PREPARING` 또는 `TRANSFERRED`에서 준비 당시 이전 담당자 ID를 확인자로 선언한 경우만 허용한다. 역할의 다음 담당자 예약을 비우고 이력을 `CANCELLED`로 남긴다.
- `ACCEPTED`와 `CANCELLED`는 종결 상태다. 같은 확인자가 이미 끝낸 전달·수락·취소를 다시 요청하면 현재 표현을 반환하고, 다른 확인자나 허용되지 않은 상태 전환은 거절한다.

### 전달 준비도 스냅샷과 경고

전달 시점에 보관되지 않은 활성 인수인계 항목 수, 그중 미완료 항목 수와 역할 자료 수를 역할 인수인계에 스냅샷한다. 다음 조건 중 하나라도 있으면 준비도 경고가 있다.

- 활성 인수인계 항목이 없다.
- 미완료 인수인계 항목이 하나 이상이다.
- 역할 자료가 없다.

경고가 있으면 요청자가 `warningAcknowledged: true`로 명시적으로 확인해야 전달할 수 있다. 이 확인은 누락을 해결했다는 뜻이 아니라 알고도 전달을 진행했다는 기록이다. 스냅샷은 전달 뒤 항목이나 자료의 현재 개수와 다시 계산하지 않는다.

### 변경 동결

- `PREPARING`에서는 준비 때 고정한 현재·다음 담당자와 담당 기간만 바꿀 수 없다. 역할 이름·목적·책임·위험, 인수인계 항목과 자료는 전달 전까지 보완할 수 있다.
- `TRANSFERRED`에서는 수락자가 확인한 범위를 유지하도록 역할 전체와 해당 역할의 인수인계 항목·자료 생성, 수정, 완료, 보관·복원과 소유 역할 이동을 막는다.
- 인수인계 항목이나 자료를 역할 사이에 옮길 때는 출발·도착 역할을 UUID 순서로 함께 잠그고 어느 쪽에도 `TRANSFERRED` 인수인계가 없는지 확인한다.
- 수락 또는 취소가 끝나면 위 동결을 해제한다.

### 시즌 경계

- 열린 역할 인수인계가 있는 시즌은 종료할 수 없다.
- 열린 역할 인수인계가 있는 원본 시즌에서는 다음 시즌을 시작할 수 없다.
- 다음 시즌에는 역할 인수인계 이력을 복사하지 않는다. 완료·취소한 이력은 역할, 인수인계 항목과 자료와 함께 원본 시즌에 남는다.
- 시즌 기간을 줄일 때 열린 인수인계의 다음 담당 기간을 새 범위 밖으로 밀어낼 수 없다.

### 동시성과 잠금

- 모든 변경은 ADR-0011의 `Team → Season` 부모 잠금과 종료 여부 확인 뒤에 수행한다.
- 역할 인수인계 준비·전달·수락·취소는 대상 `Role`의 배타적 쓰기 잠금을 먼저 얻는다. 기존 이력 전환은 이어서 대상 `RoleHandoff`를 배타적으로 잠근다.
- 새 참여자의 활동 상태는 UUID 순서의 `Member` 공유 잠금으로 확인한다.
- 인수인계 항목·자료 변경은 대상 역할을 공유 잠금한 뒤 열린 `RoleHandoff`도 공유 잠금의 최신 읽기로 조회해 `TRANSFERRED` 상태가 아닌지 확인한다. 자식 엔티티를 먼저 읽어 MySQL `REPEATABLE READ` 스냅샷이 생겼더라도 오래된 `PREPARING` 상태를 재사용하지 않으며, 역할 인수인계 전환의 배타 잠금과 직렬화되어 전달 뒤 자식 변경이 끼어들지 않는다.
- `RoleHandoff`와 다른 공유 애그리거트에는 낙관적 잠금 `version`을 유지하고, 잠금·저장 충돌은 `409 WORKSPACE_CONTENT_CONFLICT`로 처리한다.
- 서비스 검증과 별도로 MySQL의 생성 열 `active_role_id`와 고유 제약으로 역할당 열린 인수인계 하나를 보장한다.

### 멱등성과 HTTP 계약

- 준비는 새 이력을 만드는 `POST`이므로 기존 콘텐츠 생성 멱등 저널에 `ROLE_HANDOFF` 작업을 추가하고 `Idempotency-Key`를 요구한다. 같은 키와 같은 정규화 요청은 같은 이력의 현재 표현을 반환한다.
- 전달·수락·취소는 기존 이력의 상태 설정이므로 별도 생성 멱등 키를 요구하지 않는다.
- 네 API는 역할 경로 아래에 두고 응답은 전환 뒤 전체 `role`과 `handoff`를 함께 반환한다.
- 준비 성공은 `201 Created`와 역할 인수인계 URI `Location`, 나머지 전환은 `200 OK`를 사용한다.
- 상태·참여자·역할 스냅샷 불일치는 `ROLE_HANDOFF_STATE_CONFLICT`, 준비도 경고 미확인은 `ROLE_HANDOFF_WARNING_CONFIRMATION_REQUIRED`, 없는 이력은 `ROLE_HANDOFF_NOT_FOUND`로 구분한다.

### 공유 키 신원 경계

`confirmedByMemberId`와 상태별 확인자 필드는 공유 키를 가진 요청자가 이전 또는 다음 담당자 명의로 확인했다고 선언한 값이다. 현재 파일럿에는 사용자별 로그인 신원, 전자 서명이나 역할별 권한이 없으므로 실제 사람이 그 구성원인지 인증한 감사 증거로 사용하지 않는다. 이 한계는 계정·초대·권한·감사 모델을 도입할 때 다시 결정한다.

### 스키마 이관

Flyway V13은 `role_handoffs`를 만들고 팀·시즌·역할·구성원 복합 외래 키, 취소 확인자를 이전 담당자로 제한하는 상태·시각·스냅샷·경고 확인 CHECK 제약, 낙관적 잠금 버전과 열린 인수인계 유일 제약을 추가한다. 팀 소속 구성원 복합 참조를 위해 `members(id, team_id)` 유일 키도 추가한다. 콘텐츠 생성 멱등 작업에는 `ROLE_HANDOFF`를 추가한다.

기존 역할에서 과거 교대 시점이나 확인자를 복원할 근거가 없으므로 기존 데이터에 역할 인수인계 이력을 합성하지 않는다. 역할 인수인계 이력은 V13 적용 뒤 시작한 교대부터 남는다.

## 결과

### 장점

- 역할 담당 필드의 현재값과 교대 과정·과거 이력을 구분할 수 있다.
- 다음 담당자가 전달 시점의 준비도와 누락 경고를 확인한 뒤 수락한다.
- 수락과 역할 담당자·기간 변경이 한 트랜잭션으로 끝나 중간 상태가 남지 않는다.
- 전달 뒤 확인 범위를 동결하고 시즌 전환과의 모호한 경쟁을 막는다.
- 응답 유실로 준비 요청을 재시도해도 열린 인수인계가나 이력이 중복되지 않는다.

### 비용과 한계

- 역할, 역할 인수인계, 인수인계 항목과 자료 사이의 잠금 순서와 동결 규칙을 모든 변경 경로에서 유지해야 한다.
- 전달 시점 수치는 준비도 스냅샷일 뿐 항목의 내용이나 외부 자료 링크의 가용성을 보증하지 않는다.
- 현재 역할에는 최신 담당자와 기간만 남는다. V13 이전의 과거 역할 배정과 역할 인수인계를 거슬러 복원하지 않는다.
- 공유 키 확인은 선언적 참여자 확인이며 사용자별 감사 이력이 아니다.
- 다음 담당자가 전달 뒤 내용을 보완해야 한다면 먼저 취소하고 보완한 뒤 새 역할 인수인계를 준비해야 한다.

## 대안

### 역할 필드만 직접 수정

구현은 단순하지만 준비·전달·수락과 과거 교대 이력을 구분하지 못하고 두 담당자의 확인도 남지 않아 채택하지 않았다.

### 인수인계 항목에 교대 상태 추가

체크리스트 항목과 역할 담당자 전환은 생명주기와 원자성 경계가 다르다. 항목 하나의 완료가 역할 전체의 교대를 대표하게 되므로 채택하지 않았다.

### 경고가 있으면 전달을 완전히 금지

누락을 줄이지만 실제 운영에서는 자료가 불필요하거나 미완료 항목을 그대로 넘겨야 할 수 있다. 명시적 확인과 스냅샷으로 예외를 드러내는 방식을 채택했다.

### 준비 시 즉시 역할 담당자를 변경

다음 담당자가 내용을 확인하기 전에 현재 운영 책임이 바뀌고 취소 복구가 어려워 채택하지 않았다.

## 검증

```bash
./gradlew --no-daemon :application:policyTest
./gradlew --no-daemon :application:useCaseTest
./gradlew --no-daemon :adapter-in-web:restDocsTest
./gradlew --no-daemon checkApiContract
```

상태 전환과 확인자, 준비도 경고·스냅샷, 역할당 열린 이력 하나, 담당 기간의 원자적 전환, 준비·전달 상태별 변경 동결, 시즌 종료·전환 차단, 동시 요청과 V13 이관을 확인한다. REST Docs와 생성 계약에서는 네 오퍼레이션의 경로·요청·응답·오류와 워크스페이스 프로젝션을 고정한다.
