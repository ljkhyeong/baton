# ADR-0003: 첫 파일럿 단일 호스트 동일 출처 HTTPS 배포

- 상태: 채택
- 결정일: 2026-07-21

## 배경

BATON의 첫 실제 사용자는 한 그룹 스터디의 구성원들이다. 개발용 Vite와 `bootRun`을 각자 실행하는 방식으로는 공유 링크가 다른 기기의 `localhost`를 가리키고, 프로세스 재시작·TLS·데이터 백업을 보장할 수 없다.

초기 파일럿은 운영 인력이 적고 트래픽도 작다. 따라서 클라우드 공급자나 다중 호스트 구조를 먼저 고정하기보다, 한 서버에서 재현 가능하게 실행하면서 브라우저와 API를 같은 HTTPS 출처로 제공하는 최소 운영 경계가 필요하다.

## 결정

첫 파일럿은 `compose.production.yml`을 사용하는 단일 호스트 Docker Compose 배포를 채택한다.
ROUND 런타임을 같은 공개 출처에 선택적으로 활성화하는 후속 결정은 [ADR-0018](../0018_round-production-runtime/adr.md)이 소유한다. 기본 `app`·`web`·MySQL 배포와 백업 볼륨 경계는 이 결정에 남는다.

```text
인터넷
  │ 80/443
  ▼
Caddy ── 정적 React 애플리케이션
  │ /api/*, /actuator/health
  ▼
Spring Boot
  │ Docker 내부 데이터 네트워크
  ▼
MySQL
```

### 동일 출처와 TLS

- Caddy가 `BATON_HOST`의 인증서를 자동 관리하고 정적 프런트엔드를 제공한다.
- `/api/*`와 공개 서비스 상태 경로만 Spring 애플리케이션으로 역방향 프록시한다.
- 프런트엔드와 제품 API는 같은 출처를 사용하므로 개발 프록시 주소나 사용자 기기의 `localhost`가 공유 링크에 포함되지 않는다.
- Caddy는 CSP, HSTS, 리퍼러, MIME 스니핑과 브라우저 권한 관련 최소 보안 헤더를 설정한다.
- Vite가 콘텐츠 해시를 붙인 `/assets/*` 파일은 1년 `immutable`로 캐시하고, 새 배포의 자산 경로를 가리키는 진입 문서와 SPA 대체 문서는 `no-cache`로 매번 재검증한다.

### 네트워크와 런타임

- 호스트에는 Caddy의 80/443 포트만 공개한다.
- Spring 애플리케이션 포트와 MySQL 포트는 호스트에 게시하지 않는다.
- MySQL은 외부 연결이 없는 내부 `data` 네트워크에 두고 애플리케이션만 두 네트워크를 연결한다. JDBC 연결도 TLS를 요구한다. 현재 단일 호스트 내부 네트워크의 `sslMode=REQUIRED`는 전송 암호화를 강제하지만 서버 CA와 호스트 신원 검증까지 제공하지는 않는다.
- MySQL을 외부 호스트·관리형 DB·다중 호스트 구성으로 옮기기 전에는 신뢰할 CA 묶음의 배포·회전 절차와 접속 호스트명이 인증서 SAN에 포함되는지 검증하는 절차를 먼저 마련하고, 애플리케이션 JDBC와 운영 상태 검사를 모두 `VERIFY_IDENTITY`로 전환한다. 이 준비와 실제 연결 검증 없이 외부 DB 전환을 진행하지 않는다.
- 프로덕션 Compose 프로젝트와 DB 볼륨 이름을 고정해 같은 저장소의 로컬 Compose 데이터와 재사용되지 않게 한다.
- 컨테이너에는 재시작 정책, 제한된 로그 크기, 애플리케이션 상태 검사와 정상 종료 시간을 둔다.
- MySQL 상태 검사는 애플리케이션 DB 계정과 TLS로 `SELECT 1`이 성공해야 준비 완료로 판정한다.
- 계정 인증은 단일 `app` 인스턴스의 메모리 서버 세션을 사용한다. 현재는 Redis와 Spring Session 의존성을 두지 않고, 다중 복제본 전에 공유 세션 저장소를 먼저 결정한다.
- Caddy는 제품 API와 서비스 상태 요청 본문을 1MB로 제한한다.
- Spring이 만든 제품 API 응답의 `X-Request-ID`는 Caddy가 보존하고 최종 응답 헤더로 접근 로그에 기록한다. 1MB 제한과 업스트림 장애처럼 Caddy가 직접 만드는 제품 API 오류에는 Caddy가 자체 UUID를 누락된 헤더에만 채우며 접근 로그의 내장 `uuid`도 같은 값을 사용한다.
- Caddy 접근 로그는 운영 문의에 필요한 엣지 요청 ID를 남기되 `X-Baton-Access-Key`, 생성·복구 키, `Idempotency-Key`와 외부 `X-Request-ID` 필드를 제거한다. 애플리케이션 오류의 상세와 스택 트레이스는 Spring 로그에만 남는다.

### 설정과 생성 경계

- 도메인, DB 자격 증명, `BATON_WORKSPACE_CREATION_KEY`와 `BATON_WORKSPACE_RECOVERY_KEY`는 추적하지 않는 `.env.production`에서 주입한다. OAuth 클라이언트 비밀, SMTP 비밀번호, 안정적인 이메일 아웃박스 AES-256-GCM 키, BRIEF 이벤트 수신 Bearer와 ROUND PEM은 환경에 원문을 넣지 않고 저장소 밖 소유자 전용 파일의 절대 경로만 기록한다.
- 예시 환경 파일은 실제 비밀값을 제공하지 않는다. `ops/validate-production-env.sh`는 소유자 전용 일반 파일과 Git 비추적, 리터럴 허용 목록, 공개 DNS 형식, DB 식별자와 독립 생성한 32~200자 URL 안전 비밀 정책을 소유한다. 전용 인증 검증기는 Google·Naver 동시 완성, 로컬 등록과 SMTP의 폐쇄형 실패 관계, 단일 값 비밀 파일 경계, RSA 크기·쌍·`kid`를 검증한다. 배포 사전점검은 이 검증에 Linux 로컬 Docker 소켓·Compose v2와 최종 조립 확인을 더한다. DNS 전파, 외부 포트 접근, 공인 인증서 발급과 호스트 용량은 이 정적 점검의 보장 범위가 아니다.
- `ops/production-compose.sh`는 명령마다 공통 환경 검증을 다시 실행한다. 충돌할 수 있는 Compose·Docker·BuildKit 변수를 제거하고 `unix:///var/run/docker.sock`, `baton-production` 프로젝트와 Compose 파일을 고정한다.
- 기동·중지·백업·복구는 소유자 전용 미리 만든 `/srv/baton/state/production-lifecycle.lock`의 `flock`으로 직렬화한다.
- 운영 명령은 허용 목록만 실행한다. 일회성 `run`, `attach`, 모델 변환, 이미지 게시, 확장, 볼륨 삭제와 토폴로지 재정의는 거부한다. `config`는 `--quiet`만 허용한다.
- BATON 비밀값은 Spring 구성 트리 파일로, ROUND TURN 비밀값은 소유자 전용 파일로 전달한다. 다음 Compose 호출에서도 환경과 비밀 파일을 다시 검증한다.
- 개발용 DB 기본값은 `local` 프로필에만 둔다. `production`은 MySQL JDBC 주소, 비루트 사용자와 32~200자 비밀번호를 애플리케이션 기동 전에 검증한다.
- JDBC URL은 단일 `host[:port]/database` 형식이어야 하며 `sslMode=REQUIRED`, `VERIFY_CA`, `VERIFY_IDENTITY` 중 하나만 허용한다. 프래그먼트·중복·호스트별 속성을 거부하고, Hikari·JNDI·Flyway 별도 연결로 검증을 우회할 수 없다.
- 생성 키와 복구 키는 모든 프로필에서 URL 안전 ASCII 형식이어야 한다. `production`에서는 두 값을 모두 설정하고 서로 다르게 사용한다.
- 생성 키는 공개된 생성 API를 파일럿 운영자에게 제한한다. 별도의 복구 키는 모든 구성원이 워크스페이스 접근 키를 잃었을 때만 사용하며 두 값을 서로 다르게 생성한다.
- 최종 계정·초대·권한 모델은 이 결정에 포함하지 않는다.

### 백업과 복구

- `ops/backup.sh`는 컨테이너 내부 루트 자격과 `--single-transaction`, `--hex-blob`을 사용해 일관된 MySQL 덤프를 호스트의 권한 제한 압축 파일로 만든다. 비밀번호는 프로세스 인자에 넣지 않으며, 실행별 고유 임시 파일과 원자적 이동으로 동시 실행의 덮어쓰기를 막는다. gzip과 BATON 핵심 스키마 표식을 검증하고 필수 SHA-256 체크섬 사이드카를 먼저 게시한 뒤 덤프 본문을 마지막에 공개해 비정상 종료 중 불완전 본문이 동기화 글롭을 막지 않게 한다.
- `ops/verify-backup.sh`는 gzip·스키마 표식과 SHA-256 체크섬 사이드카를 공통 검증한다. `ops/restore.sh`는 체크섬 사이드카를 필수로 요구하고 예약 백업 잠금과 프로덕션 Compose 생명주기 잠금을 모두 잡으며, 명시적인 확인 환경 변수와 절대 경로를 요구한다. `app`·`web`·ROUND 웹·ROUND 시그널링 컨테이너가 모두 `exited` 상태가 아니면 일시 중지·재시작 중 상태를 포함해 복구를 차단한다. 오프라인 복구는 대상 DB를 삭제하고 다시 만든 뒤 덤프를 주입해 백업 이후 추가된 테이블과 데이터까지 제거하고 핵심 테이블을 다시 확인한다.
- 과거 스냅샷은 복원 시점까지의 접근 키 폐기 상태를 포함하지 않을 수 있으므로, `restore.sh`는 성공을 알리기 전에 모든 팀의 `access_key_hash`를 팀별 CSPRNG 값으로 교체한다. V2 이상 스키마에서는 같은 트랜잭션에서 마지막 키 변경 멱등 표식을 `NULL`로 만들고 버전을 증가시킨다. 이미 사용한 키 변경 이력과 워크스페이스·콘텐츠 생성 멱등 이력은 과거 요청을 새 요청으로 되살리지 않도록 보존한다. V1 스키마는 접근 키만 먼저 무효화하고 이후 애플리케이션 기동 때 Flyway가 널 허용 표식과 버전을 추가한다.
- 무효화한 팀 수, 저장 해시 형식과 남은 최신 표식을 검증하고 각 팀에 복구용 최신 대표 시즌이 하나씩 없으면 복구를 실패시킨다. 대표 시즌은 시작일과 UUID 내림차순의 첫 행으로 고른다. 성공한 복구 대상은 서비스 사용자만 읽는 백업 상태의 `last-restore-recovery-targets.tsv`에 기록한다. 복원 뒤 모든 기존 공유 링크는 폐기되며, 운영자는 각 팀을 새 멱등 키로 복구한 뒤 새 링크를 다시 배포하고 그 상태를 새로 백업해야 한다.
- `ops/backup-cycle.sh`는 systemd 사용자 타이머의 진입점이다. `0700` 상태 디렉터리의 동일 잠금을 복원과 공유하고 열린 파일 디스크립터의 `flock`으로 주기 전체를 직렬화하므로, 파일은 남아도 프로세스 종료 뒤 실제 잠금은 자동 해제된다. 이전 주기의 미업로드 파일을 먼저 재시도하되 그 재시도만으로 최신성과 로컬 보존 상태를 바꾸지 않고, 이어서 새 덤프를 생성한다.
- `ops/sync-backups.sh`는 rclone 1.64 이상에서 영문·숫자·밑줄 이름의 공급자 독립 `crypt` 원격 저장소만 허용하며 설정과 환경의 `no_data_encryption` 재정의도 거부한다. 각 덤프와 필수 SHA-256 체크섬 사이드카를 `copyto --immutable`로 올리고 `rclone check --download --one-way`로 해당 두 파일의 내용을 비교해 일치해야 전체 원격 성공으로 판정한다. 완전히 검증한 파일에는 해시와 원격 저장소를 가진 로컬 완료 표식을 원자적으로 기록해 이후 주기에는 미완료 파일만 재시도한다. 일반 원격 저장소, 기존 원격 객체 불일치, 업로드·재다운로드 실패에는 완료 표식, 스냅샷 성공 상태와 보존 정리를 갱신하지 않는다.
- 완전히 검증된 원격 성공 뒤 14일이 지난 로컬 덤프와 체크섬 사이드카를 정리하되 최신 세 세트는 항상 보존한다. 삭제 직전에는 같은 rclone 검사로 해당 원격 본문과 체크섬 사이드카를 재검증하며, BATON은 원격 객체를 삭제하지 않는다. 원격 보존 기간, 버전 관리, 생명주기와 객체 잠금은 선택한 공급자의 전용 BATON 경계에서 결정한다.
- 사용자 타이머는 매일 `03:15 Asia/Seoul`부터 최대 15분 안에 실행하고 `Persistent=true`로 놓친 실행을 기동 뒤 보충한다. 서비스 실패는 15분 간격으로 재시도하되 시작률을 1시간에 네 번으로 제한하며 저널에 남긴다. 무로그인 기동에는 해당 사용자의 linger가 필요하다.
- 체크섬에 결합된 UTC 파일명에서 외부 검증 최신 스냅샷 시각을 구하고 이름·해시·검증 시각과 함께 기록해 36시간 최신성 검사를 제공하지만 실제 가져오기 성공을 대신하지 않는다. 암호화 설정·암호·솔트와 공급자 자격은 해당 암호화 원격 저장소와 다른 복구 경계에도 보관하고, 실제 데이터 투입 전과 이후 월 1회 다른 환경에서 다운로드·복호화·복구 리허설을 수행한다.
- 자동 품질 관문의 복구 리허설은 운영 래퍼에 프로젝트 재정의를 추가하지 않는다. 대신 현재 `backup.sh`·`restore.sh`·검증 SQL을 소유자 전용 임시 경계에 그대로 복사하고, 테스트 전용 Compose 심이 고유 프로젝트·실행 토큰·동일 Docker 데몬/컨텍스트·사용자 정의 레이블·전용 볼륨과 DB 이름·중지된 `app`/`web`을 매 명령에서 확인한 뒤 폐기 가능한 DB에만 연결한다. 같은 데몬에 `baton-production` 리소스가 있거나 예상 이름의 기존 볼륨·네트워크·이미지가 있으면 시작 전에 거부한다. 이 리허설은 실제 덤프/가져오기와 키 복구 사슬을 증명하지만 암호화 원격 저장소 다운로드와 별도 호스트 복구를 대신하지 않는다.

### 운영 상태 감지

- `baton-service-health.timer`는 기동 2분 뒤부터 5분마다 공개 HTTPS 서비스 상태를 호출한다. 리디렉션과 신뢰되지 않은 인증서를 허용하지 않고 TLS 1.2 이상, HTTP 200과 종합 상태 `UP`을 요구해 DNS·공인 TLS·Caddy·Spring·DB 서비스 상태 경계를 관통한다.
- `baton-backup-freshness.timer`는 기동 3분 뒤부터 1시간마다 외부 재읽기 검증 성공 상태를 확인한다. 상태 파일은 서비스 사용자 소유의 일반 파일이어야 하고 스냅샷 파일명 UTC 시각과 저장 에포크, 검증 시각의 순서, 원격 저장소 형식과 36시간 경계를 모두 만족해야 한다.
- 두 일회성 서비스는 자동으로 Compose를 재시작하거나 데이터를 바꾸지 않는다. 성공은 0, 실패는 0이 아닌 값으로 끝나고 표준 출력·표준 오류를 저널에 남긴다. 서비스 상태와 최신성은 장애 특성과 주기가 달라 각 유닛의 실패 상태와 향후 알림 연동 지점을 분리한다.
- 동일 호스트 타이머는 호스트 전원·커널·전체 네트워크 장애를 감지하거나 알릴 수 없다. 기본 비활성화된 GitHub Actions `외부 상태 감시`를 첫 외부 관측 경계로 두고, 배포 뒤 저장소 변수 `BATON_HEALTH_URL`의 수동 검사를 통과한 경우에만 `BATON_EXTERNAL_MONITOR_ENABLED=true`로 예약 검사를 켠다. 비공개 저장소 실행기 사용량을 제한하려고 기본 브랜치에서 매시 17분에 한 번 실행하며 로컬 검사와 같은 엄격한 공개 HTTPS 서비스 상태 검사를 30초 간격으로 최대 두 번 수행한다.
- GitHub 예약 실행은 지연되거나 누락될 수 있고 실패 알림의 수신자는 워크플로 생성·cron 수정·재활성화 주체와 개인 Actions 알림 설정에 의존한다. 이 워크플로는 독립적인 호출·SMS 알림을 제공하지 않으므로 보조 감시 수단이다. 더 짧은 감지 시간이나 독립 알림이 필요하면 다른 네트워크의 가동 상태 모니터링 서비스와 채널을 같은 공개 서비스 상태 URL에 추가한다. NAT 루프백·분할 DNS에서는 로컬 검사만 실패할 수 있다.
- 서비스 상태 검사 성공은 정적 프런트엔드·공유 링크 쓰기와 실기기 동기화를, 최신성 검사 성공은 원격 객체의 현재 재검증이나 실제 MySQL 가져오기를 보장하지 않는다.

### 선택 외부 백업 감시

`BATON_BACKUP_HEARTBEAT_URL_FILE`을 설정하면 새 백업의 원격 검증을 마친 뒤 Better Stack의 하트비트 API에 완료 신호를 보낸다. 기대 간격과 유예 시간 안에 신호가 없으면 외부 서비스가 알림을 보내므로 홈서버 중단도 감지할 수 있다. 기존 대기 백업 재전송만으로는 완료 신호를 보내지 않는다. 감시 API 장애는 이미 완료된 백업의 재실행 원인으로 사용하지 않는다.

무료 한도, 비밀 URL 관리와 활성화 검증은 [무료 외부 연동](../../runbooks/free-integrations.md#백업-하트비트)을 따른다. 이 연동은 백업 스케줄러와 분리하며 k3s 설치나 기존 Compose 배포 경계를 변경하지 않는다.

### 선택 내부 연동 경보

기존 Micrometer 지표를 Prometheus 경보 규칙과 Alertmanager의 SMTP 수신기에 연결한다. 지표 수집 불가·갱신 오류와 실제 조치 대상 전달 실패·처리 지연을 구분하며, 알림 묶기·재통지·해제는 Alertmanager가 맡는다. BATON에는 별도 경보 발송기를 추가하지 않는다.

루프백 전용 지표 접근을 유지하기 위해 수집기는 앱과 네트워크 공간을 공유한다. 수집·경보 규칙·SMTP 예시와 로컬 검증을 제공하며 실제 실행 환경 연결과 메일 수신 검증은 남아 있다. 활성화 후 기존 연동 점검 타이머의 중복 실행을 끄고 외부 호스트 장애 감시는 유지한다. 설정과 경보 기준은 [내부 연동 장애 알림](../../runbooks/free-integrations.md#내부-연동-장애-알림-prometheus--alertmanager)을 따른다.

## 결과

### 장점

- 실제 공유 URL, TLS와 API 출처를 하나의 배포 단위로 재현할 수 있다.
- DB가 인터넷이나 LAN에 직접 노출되지 않는다.
- 작은 파일럿에 현재 불필요한 세션 저장소와 다중 서비스 운영 비용을 줄인다.
- 백업과 복구의 실행 경로가 저장소에 남는다.

### 비용과 한계

- 단일 호스트 장애 시 서비스가 중단되므로 외부 백업과 호스트 모니터링이 필요하다.
- 호스트 로컬 상태 감지는 실패를 저널에 남기고 GitHub 센티널은 호스트 전체 장애를 보조 관측하지만, 예약 실행의 지연·누락과 독립적인 사용자 호출을 해결하지 않으므로 필요한 감지 시간에 맞는 외부 모니터·알림 연결이 별도로 필요하다.
- 외부 백업은 systemd·flock·rclone과 서비스 사용자의 Docker 소켓 접근에 의존한다. 루트 권한 Docker의 docker 그룹은 사실상 루트 권한이며 이 자동화가 별도 권한 격리를 제공하지 않는다.
- 암호화 원격 저장소 설정과 복호화 자격을 잃으면 원격 객체가 정상이어도 복구할 수 없다. 최신성 검사 성공은 MySQL 가져오기 성공을 증명하지 않는다.
- 복구는 의도적으로 모든 공유 링크를 폐기하므로 팀별 접근 키 재발급과 구성원에게 새 링크를 전달하는 운영 시간이 필요하다.
- 자동 무중단 배포, 다중 인스턴스와 DB 고가용성을 제공하지 않는다.
- Caddy의 자동 인증서를 위해 올바른 공개 DNS와 80/443 접근이 필요하다.
- 단일 호스트 내부 MySQL 연결은 암호화하지만 CA와 호스트 신원까지 검증하지 않는다. 외부 DB 전환 전에는 CA 배포·회전, SAN 검증과 `VERIFY_IDENTITY` 전환을 완료해야 한다.
- 품질 관문은 검증용 이미지를 빌드하지만 레지스트리 게시와 호스트 배포는 수동이며 공급자별 IaC는 포함하지 않는다.

## 대안

### 개발 서버를 LAN에 직접 공개

구성은 단순하지만 TLS, 출처, 프로세스 복구와 데이터 저장소 노출을 안정적으로 통제하기 어려워 채택하지 않았다.

### 초기부터 관리형 클라우드와 Kubernetes 사용

확장성과 관리 기능은 좋지만 첫 스터디 파일럿의 트래픽과 운영 인력에 비해 복잡도가 크고 제품 검증보다 인프라 결정을 앞세우므로 보류했다.

## 검증

```bash
bash ops/check-shell-scripts.sh
bash ops/tests/backup-cycle-test.sh
bash ops/tests/pilot-readiness-test.sh
bash ops/tests/production-runtime-smoke.sh
systemd-analyze verify ops/systemd/baton-backup.service ops/systemd/baton-backup.timer ops/systemd/baton-service-health.service ops/systemd/baton-service-health.timer ops/systemd/baton-backup-freshness.service ops/systemd/baton-backup-freshness.timer
systemd-analyze calendar '*-*-* 03:15:00 Asia/Seoul'
./ops/preflight-production.sh
./ops/production-compose.sh up -d --build
```

GitHub Actions 품질 관문은 풀 리퀘스트와 `main` 푸시에서 백업 성공·스키마 실패·비암호화 저장소 거부·원격 체크섬 사이드카 실패·업로드 성공 뒤 로컬 보존 흐름을 확인한다.

별도 셸 픽스처는 프로덕션 환경 파일 권한·리터럴 문법·비밀 분리, 주변 환경 제거, HTTPS 건강 상태의 성공·실패 종료와 백업 UTC 상태 교차검증을 고정하고 백업·모니터 systemd 유닛 문법을 확인한다.

복원 픽스처는 현재 스키마와 V1 스키마 분기, 팀 수와 키 무효화 수 불일치 거부, 팀별 복구 대상 기록을 확인한다.

프로덕션 패키지 작업은 고유 프로젝트에서 이미지를 빌드한 뒤 DB 설정이 없는 `app` 이미지가 컨텍스트와 Flyway 구성 전에 실패하는지 먼저 확인한다. 이어서 폐기 가능한 볼륨으로 같은 이미지를 실행해 Caddy 내부 CA의 TLS 종단, 정적 화면·SPA 대체 경로, 건강 상태·제품 API 프록시와 보안 헤더, 유효한 CI 전용 키를 사용한 프로덕션 프로필 기동, 빈 DB Flyway 마이그레이션, 호스트에 게시되지 않은 `app`·MySQL 포트와 암호화된 JDBC 세션을 실제 운영 비밀 없이 검증한다.

제품 API의 정상 Spring 요청 ID 보존과 대용량 413·중지된 업스트림 502/503의 Caddy 요청 ID·접근 로그 상관관계, 운영 키·멱등 키 로그 제거도 실제 엣지에서 확인한다.

이어서 두 실제 워크스페이스와 후속 시즌을 만들고 원본 `backup.sh`·`restore.sh`로 스냅샷 롤백, 팀별 최신 복구 대상, 모든 과거 키 폐기와 동일 재처리 툼스톤, 운영자 복구·새 키 조회와 변경·재백업을 검증한다.

실패 상태는 환경 변수를 제외한 검사 정보와 보호 값이 없는 로그만 산출물로 보존하고, 소유 레이블을 확인한 스모크 전용 컨테이너·네트워크·볼륨·이미지만 제거한다.

외부 서비스 상태 감시는 코드 품질 관문과 분리하며, 명시적으로 활성화한 배포 URL의 현재 도달성을 예약 검사한다.

이 검증은 이미지를 게시하거나 실제 원격 저장소·호스트에 배포하지 않는다. 셸 픽스처는 실제 DNS·공인 CA·타이머 실행을 대신하지 않고 유닛 정적 검증도 linger·저널·실패 후 다음 주기 회복을 증명하지 않는다. Caddy 내부 CA는 공인 DNS·ACME와 브라우저 신뢰 체인을 대신하지 않으며, 외부 80/443 방화벽, HTTP/3, 실제 암호화 원격 저장소 업로드, 타이머 재기동, 기존 운영 데이터 마이그레이션과 실기기 공유 동작은 운영 환경에서 별도로 확인한다.

실제 배포 뒤에는 `/actuator/health`와 서로 다른 두 기기의 공유 링크 조회·변경을 확인한다. 예약 상태 검사은 `BATON_EXTERNAL_MONITOR_ENABLED`가 없거나 `false`이면 건너뜀 상태다. 수동 실행과 활성화된 예약 실행은 건강 상태 URL이 없거나 유효하지 않으면 폐쇄형 실패하며, 실제 URL을 사용한 수동 성공과 첫 예약 실행의 정시성·알림 전달은 운영 환경에서 별도로 확인한다.
