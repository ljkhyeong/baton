# ADR-0007: 결정과 바통을 가역 보관하고 같은 조회 모델로 복원

- 상태: 채택. 결정·바통 범위는 유지하며 회차 수정·보관 제외 범위는 ADR-0008, 바통의 시즌 소유 경계는 ADR-0011로 보완
- 결정일: 2026-07-24

## 배경

그룹 스터디 파일럿 사용자는 잘못 기록한 결정과 바통 항목을 바로잡고, 현재 운영 화면에서는 치우되 조직의 기억은 잃지 않아야 한다. 영구 삭제는 결정 이유와 인수인계 맥락을 복구할 수 없게 만들고, 별도 조회 계약 없이 보관 기록을 조회 모델에서 제외하면 새로고침 뒤 복원할 방법도 사라진다.

생성 API의 멱등 재생은 최초 리소스의 현재 표현을 돌려준다. 따라서 생성 뒤 수정하거나 보관한 기록도 활성 기록을 다시 만든 것처럼 보이지 않고 현재 상태가 일관되게 표현되어야 한다.

## 결정

- 결정과 바통 항목은 생성 요청과 같은 업무 필드를 받는 전체 `PUT` 수정 API를 제공한다.
- 두 기록은 `{ "archived": true | false }`를 받는 `PATCH .../archive` API로 보관하고 복원한다.
- `Decision`과 `HandoffItem`에 `null`을 허용하는 `archived_at`을 둔다. `true`로 처음 보관할 때 서버 `Clock`의 UTC `Instant`를 기록하고, 같은 상태를 반복 요청하면 최초 보관 시각을 유지한다. `false`는 값을 `null`로 되돌린다.
- 워크스페이스 조회 모델의 기존 `decisions`와 `handoffItems` 배열에는 활성·보관 기록을 모두 포함한다. 응답에서 `null`을 허용하는 `archivedAt`을 기준으로 프런트엔드가 일반 화면과 보관함을 나눈다.
- 보관 상태에서는 일반 내용 수정과 바통 완료 변경을 허용하지 않고 찾지 못한 활성 기록과 같은 `404`로 응답한다. 보관 API만 보관 상태를 다시 활성 상태로 복원할 수 있다.
- 결정 응답에는 표시용 `authorName`과 함께 안정적인 수정 입력용 `authorMemberId`를 제공한다. 클라이언트는 이름으로 작성자 식별자를 역추론하지 않는다.
- 낙관적 잠금의 저장소 `version`은 ADR-0005에 따라 유지하되 HTTP DTO에는 노출하지 않는다.
- 보관은 영구 삭제가 아니다. 결정·바통의 hard delete는 이번 결정에 포함하지 않는다. 이 결정에서 제외했던 회차 수정·보관은 이후 ADR-0008이 별도 불변식과 동시성 경계를 포함해 채택한다.

## 결과

### 장점

- 별도 보관 조회 API 없이 새로고침 뒤에도 기록을 찾아 복원할 수 있다.
- 생성 멱등 재생과 워크스페이스 조회 모델이 수정·보관된 현재 표현을 같은 방식으로 보여 준다.
- 영구 삭제 없이 일상 화면의 잡음을 줄이면서 결정과 인수인계 맥락을 보존한다.
- 활성·보관 상태가 한 projection에 있어 여러 사용자의 화면이 같은 기준으로 수렴한다.

### 비용과 한계

- 조회 모델 크기가 늘고 모든 소비자가 `archivedAt`으로 활성 기록을 명시적으로 걸러야 한다. 이 필터를 빠뜨리면 진행률, 최신 결정과 바통북 계산이 보관 기록에 오염될 수 있다.
- 현재 값과 보관 시각만 남기므로 수정 이력이나 보관·복원 감사 로그는 제공하지 않는다.
- 바통 항목은 계속 역할을 통해 소유를 판정한다. ADR-0011 이후 역할 자체가 시즌 snapshot이므로 바통도 원본 역할의 시즌에 남고 다음 시즌에 자동 복사되지 않는다.
- 저장소 버전을 클라이언트 사전 조건으로 보내지 않으므로 오래 열린 화면에서 순차 요청이 덮어쓰는 한계는 ADR-0005와 같다.

## 대안

### 서버에서 보관 기록 제외

일반 조회 모델은 작아지지만 새로고침 뒤 복원에 별도 목록 API가 필요하고 생성 멱등 재생의 현재 표현과 조회 결과가 어긋나므로 채택하지 않았다.

### 영구 삭제

구현과 화면은 단순하지만 실수에서 복구할 수 없고 조직 기억을 보존한다는 제품 방향에 맞지 않아 채택하지 않았다.

### 별도 보관 API와 배열

활성 조회 모델을 작게 유지할 수 있지만 조회·캐시·계약 분기가 늘어난다. 파일럿에서 조회 모델 크기가 실제 문제가 될 때 다시 검토한다.

## 검증

```bash
./gradlew --no-daemon :application:useCaseTest
./gradlew --no-daemon :adapter-in-web:restDocsTest
./gradlew --no-daemon generateApiContract
./gradlew --no-daemon checkApiContract
cd frontend && npm run typecheck
cd frontend && npm run build
```

결정과 바통을 수정하고 보관했다가 복원하는 흐름, 보관 상태의 일반 변경 거절, 반복 보관의 시각 유지, 동시에 겹친 변경의 `409` 변환, 기존 행의 `archived_at = null`·`version = 0` 이관을 확인한다. 워크스페이스 조회 모델이 활성·보관 기록을 모두 반환하고 프런트엔드가 둘을 다른 화면에 표시하는지도 확인한다.
