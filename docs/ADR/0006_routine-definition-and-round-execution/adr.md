# ADR-0006: 반복 루틴 정의와 회차별 실행 기록 분리

- 상태: 채택. 회차 생성 후 이름·날짜 불변과 보관 미지원 범위는 ADR-0008로 대체
- 결정일: 2026-07-21

## 배경

초기 파일럿은 `Routine` 한 행에 반복 업무의 제목·단계·기한·담당 역할·상세와 `WAITING` 또는 `DONE` 상태를 함께 저장했다. 이 모델에서는 한 번 완료한 상태를 다음 모임에 재사용할 수 없고, 완료를 초기화하면 어느 회차에서 수행했는지 잃는다. 이미 끝난 회차도 이후 루틴 정의 수정의 영향을 받아 과거 운영 맥락이 바뀔 수 있다.

실제 그룹 스터디에서는 같은 루틴 정의를 여러 모임에서 반복하되 각 모임의 완료 상태와 당시 실행 내용을 독립적으로 보존해야 한다. 응답 유실 뒤 회차 생성 재시도 또한 중복 회차나 중복 실행을 만들지 않아야 한다.

## 결정

### 정의, 회차와 실행의 책임

- `Routine`은 제목, `BEFORE`·`DURING`·`AFTER` 단계, 기한 문구, 담당 역할과 상세를 가진 반복 정의다. 완료 상태를 소유하지 않는다.
- `SeasonRound`는 한 시즌의 수동 운영 회차다. 사용자가 최대 100자의 `name`과 시즌 기간 안의 `meetingDate`를 입력해 생성하고 이름은 시즌 안에서 유일하다. 이 결정에서 채택했던 생성 후 메타데이터 불변 범위는 ADR-0008이 대체하며, 현재는 실행 기록을 보존한 채 이름·날짜를 정정하고 회차를 가역 보관할 수 있다.
- `RoutineExecution`은 회차를 만들 때 존재한 각 루틴의 식별자, 제목, 단계, 기한 문구, 담당 역할과 상세를 복사한 실행 스냅샷이다. 실행 상태는 `WAITING`으로 시작해 해당 회차 안에서만 `DONE`으로 바뀐다.

회차 생성 transaction은 현재 시즌의 루틴 전체를 한 번 조회하고 회차, 실행 스냅샷과 콘텐츠 생성 멱등 예약을 함께 커밋한다. 생성 뒤 루틴을 추가하거나 정의를 수정해도 이미 만든 회차의 구성과 스냅샷은 바뀌지 않고 다음 회차부터 반영된다.

### 멱등성과 동시 변경

- 회차 생성은 기존 콘텐츠 생성과 같은 `Idempotency-Key` 계약을 사용하고 작업 종류 `ROUND`로 다른 생성과 분리한다.
- 같은 키와 같은 정규화 요청을 재생하면 최초 회차 식별자와 현재 회차·실행 상태를 반환하며 실행을 다시 스냅샷하지 않는다. 현재 회차 표현에는 ADR-0008 이후의 이름·날짜·보관 상태도 포함된다.
- 데이터베이스는 `(season_id, name)`으로 회차 이름을, `(season_round_id, routine_id)`로 한 회차의 루틴 구성 중복을 막는다.
- `RoutineExecution`은 JPA `@Version`을 사용한다. 같은 실행의 완료 상태 변경이 겹치면 늦은 요청은 `409 WORKSPACE_CONTENT_CONFLICT`를 받는다.
- 루틴 정의와 실행은 다른 행이므로 정의 수정과 회차 완료 처리는 서로 충돌하거나 값을 덮어쓰지 않는다.

### HTTP 계약

다음 경로를 채택한다.

```http
POST /api/v1/teams/{teamId}/seasons/{seasonId}/rounds
PATCH /api/v1/teams/{teamId}/seasons/{seasonId}/rounds/{roundId}/routine-executions/{executionId}/completion
```

워크스페이스 projection의 `routines`는 완료 상태 없는 정의 목록이고, `rounds`는 회차와 그 안의 실행 스냅샷을 반환한다. ADR-0008 이후 회차에는 nullable `archivedAt`도 포함된다. `PATCH /api/v1/teams/{teamId}/seasons/{seasonId}/routines/{routineId}/completion`은 어느 회차의 실행인지 표현하지 못하므로 제거한다.

### 기존 데이터 이관

Flyway V5는 기존 루틴이 있는 각 시즌에 이름이 `회차 도입 이전 기록`인 회차를 하나 만든다. 기존 `routines.status`와 정의 전체를 그 회차의 실행으로 복사한 뒤 `routines.status`를 제거한다.

기존 상태에는 실제 모임 날짜가 없으므로 이관 회차의 `meeting_date`는 `NULL`로 둔다. 존재하지 않았던 날짜를 시즌 시작일 등으로 만들어 내지 않는다. 신규 회차 생성 요청에는 `meetingDate`가 계속 필수이고, 응답에서 날짜가 비어 있을 수 있는 경우는 이관 회차뿐이다. 이후 migration도 이 값을 합성하지 않으며 ADR-0008의 수정 API에서 운영자가 실제 시즌 내 날짜를 제공할 때만 채운다.

## 결과

### 장점

- 같은 루틴을 여러 회차에서 독립적으로 완료할 수 있고 이전 회차의 상태를 잃지 않는다.
- 이후 정의를 고쳐도 과거 회차의 실행 내용과 구성은 생성 당시 모습으로 남는다.
- 정의 수정과 완료 처리의 저장 행이 분리되어 서로의 값을 되돌리는 경쟁이 사라진다.
- 회차 생성 응답이 유실되어도 동일 멱등 요청으로 원래 스냅샷을 복구한다.

### 비용과 한계

- 회차마다 루틴 표시 필드를 복사하므로 저장 공간과 projection 크기가 늘어난다.
- 루틴 정의에는 활성·보관 상태가 없어 시즌의 모든 루틴 정의가 새 회차에 포함된다.
- 회차 자동 생성, 실제 마감 시각, 지연 판정, 조직 시간대와 완료한 사용자 감사 이력은 아직 제공하지 않는다.
- 이관 회차는 원본 데이터에 없던 실제 모임 날짜를 복구할 수 없다.
- 기존 루틴 완료 경로와 `routines[].status`를 사용하는 클라이언트는 새 회차 계약으로 함께 전환해야 한다.

## 대안

### 루틴 상태를 회차마다 초기화

스키마 변경은 작지만 이전 완료 상태와 실행 당시 정의를 잃으므로 채택하지 않았다.

### 실행은 상태와 루틴 ID만 저장

중복 데이터는 줄지만 이후 루틴 제목, 담당 역할이나 실행 방법을 수정하면 과거 회차의 의미도 바뀌므로 채택하지 않았다.

### 회차 조회 시 루틴 실행을 동적으로 계산

별도 실행 행을 줄일 수 있지만 회차별 구성과 독립 완료 상태를 안정적으로 보존할 수 없어 채택하지 않았다.

## 검증

```bash
./gradlew --no-daemon :application:useCaseTest
./gradlew --no-daemon :adapter-in-web:restDocsTest
./gradlew --no-daemon generateApiContract
./gradlew --no-daemon checkApiContract
```

MySQL에서 V4 데이터의 상태와 정의가 V5 실행 스냅샷으로 이관되는지, 회차 생성 뒤 루틴 추가·수정이 이전 회차를 바꾸지 않는지, 동일 생성 요청 재생이 실행을 늘리지 않는지와 같은 실행의 겹친 완료 변경이 충돌하는지를 확인한다.
