# ADR-0011: 시즌 종료와 다음 시즌 전환을 기록 경계로 관리

- 상태: 채택
- 날짜: 2026-07-30

## 배경

BATON의 첫 파일럿은 온보딩에서 한 팀과 한 시즌을 만들고 그 경로 안에서 역할, 반복 업무, 회차, 결정과 인수인계를 운영했다. 실제 그룹 스터디를 다음 기수까지 이어 가려면 운영자가 DB를 직접 다루지 않고 시즌 이름과 기간을 고치고, 현재 시즌을 종료하고, 필요한 운영 정의만 다음 시즌으로 이어 갈 수 있어야 한다.

기존 `Role`은 팀에 속하면서 이름·목적·책임뿐 아니라 현재·다음 담당자와 담당 기간을 한 행에 가진다. 워크스페이스 조회도 팀 역할 전체를 모든 시즌에 노출했다. 이 행을 다음 시즌에서 그대로 수정하면 과거 시즌의 담당 상태가 함께 바뀌고, 새 행으로 복사하면 기존 `(team_id, name)` 유일성에 막힌다. 역할을 참조하는 인수인계와 자료도 같은 문제를 가진다.

또한 접근 키는 `Team` 한 행이 소유하고 브라우저의 저장소·대기 중 기록·Web Lock도 팀 단위지만, 서버의 접근 키 회전·복구 결과는 `teamId + seasonId + idempotencyKey`로 파생했다. 다중 시즌에서는 한 시즌에서 응답을 잃은 키 변경을 다른 시즌 경로에서 재확인할 때 별도 변경으로 해석될 수 있다.

시즌 종료와 일반 콘텐츠 변경도 같은 부모 경계를 잠그지 않으면 경쟁한다. 종료 여부를 읽은 직후 역할이나 반복 업무 수정이 끼어들 수 있으므로 종료 상태만 추가하는 것으로는 읽기 전용 계약을 보장할 수 없다.

## 결정

### 시즌 상태와 계보

- `Season`은 `null`을 허용하는 UTC `endedAt`, `null`을 허용하는 `previousSeasonId`와 낙관적 잠금 `version`을 가진다.
- `endDate`는 계획한 운영 기간의 끝이고 `endedAt`은 운영자가 확정한 행정적 종료다. 날짜가 지났다는 이유로 서버가 자동 종료하지 않는다.
- 한 시즌은 최대 한 후속 시즌만 갖고, 한 팀에는 종료되지 않은 시즌을 최대 하나만 둔다.
- 종료 시즌은 계속 조회할 수 있지만 일반 콘텐츠 생성·수정·완료·보관·복원은 `SEASON_ENDED` 충돌로 거절한다.
- 예외적으로 운영자 복구 키로 보호한 이름 전용 정정은 종료 여부·후속 시즌 유무와 관계없이 허용한다.
  팀 공유 잠금과 시즌 배타 잠금, 기존 이름 규칙과 저장 경로를 재사용하고 기간·시간대·종료·계보는
  바꾸지 않는다. 일반 공유 키의 수정 권한은 그대로 두며 CAL 캡처도 원본과 함께 커밋한다.
- `PREPARING` 또는 `TRANSFERRED` 역할 인수인계가 있으면 시즌 종료와 다음 시즌 시작을 `ROLE_HANDOFF_STATE_CONFLICT`로 거절한다. 원본 시즌에서 수락 또는 취소해 역할 담당 상태를 확정한 뒤 전환한다.
- 후속 시즌이 없을 때만 종료를 되돌릴 수 있다. 후속 시즌이 있으면 과거 시즌과 현재 시즌을 동시에 활성화하지 않는다.
- 시즌 이름은 팀 안에서 유일하다.

### 역할은 시즌별 전체 스냅샷

- `Role`은 `teamId`와 `seasonId`를 함께 소유한다.
- 역할 이름은 `(season_id, name)`으로 유일하다.
- 다음 시즌으로 이어 가는 역할은 새 UUID 행으로 복제한다.
- 이름·목적·책임·위험 신호만 복사하고 현재 담당자, 다음 담당자와 담당 기간은 비운다. 이전 시즌의 예정 담당자를 새 시즌 담당자로 자동 승격하지 않는다.
- 선택한 반복 업무 정의도 새 UUID로 복제하고 담당 역할은 새 역할 UUID로 치환한다.
- 구성원은 계속 팀 범위의 식별성을 유지한다.
- 회차, 실행 상태, 결정, 인수인계 항목, 역할 인수인계 이력과 역할 자료는 복사하지 않는다. 원본 역할을 참조하는 인수인계 항목·역할 인수인계·자료는 원본 시즌에 남으므로 과거 조회 모델을 오염하지 않는다.
- 다음 시즌으로 복제한 역할과 반복 업무는 원본 식별자를 계보로 보존해 멱등 동일 재처리 응답의 원본-대상 대응 관계를 복원한다.
- 역할 응답에 기존 `previousRoleId`를 노출한다. UI는 `previousSeasonId`가 있을 때만 이전 시즌을 별도로 조회하고 원본 역할의 자료·결정·인수인계 항목을 읽는다. 필요한 자료의 제목·URL·설명을 현재 시즌의 기존 자료 생성 명령으로 전달하며 원본 UUID·생성 시각·보관 상태는 복사하지 않는다. 다음 시즌 생성 트랜잭션의 자동 복사 범위는 바뀌지 않는다.
- V11 이관 역할은 `previousRoleId`가 있어도 이전 시즌 연결이 없을 수 있다. 이 응답은 허용하되 임의의 시즌을 원본으로 추정하지 않는다.

새 역할 UUID를 사용하는 이유는 현재 애그리게이트와 외래 키 경계를 그대로 명확하게 유지하면서 과거 역할·인수인계·자료를 함께 고정하기 위해서다. 장기간 유지되는 별도 역할 식별성이 필요해지면 역할 정의와 시즌 배정 스냅샷을 분리하는 후속 결정을 내린다.

### 기존 데이터 이관

- 기존 스키마는 한 팀의 역할·인수인계·자료를 모든 시즌 워크스페이스에 같은 현재값으로 노출했다. V11은 이 동작을 잃지 않도록 이관 시점의 역할과 책임, 인수인계, 자료를 팀의 기존 시즌마다 새 UUID 스냅샷으로 복제한다.
- 시즌별 반복 업무·회차 실행·결정의 역할 참조와 역할·인수인계·자료 생성 멱등 결과는 해당 시즌 스냅샷 UUID로 다시 연결한다.
- 기존에 시즌이 여러 개인 팀은 시작일과 UUID가 가장 큰 최신 시즌 하나만 활성 상태로 남기고 나머지를 이관 시각에 종료한다. 이전 스키마에는 행정적 종료 시각이 없으므로 실제 과거 종료 시각을 복원했다고 해석하지 않는다.
- 과거 시즌별 역할 값의 변경 이력은 존재하지 않으므로 모든 이관 스냅샷은 이관 시점의 같은 값에서 시작한다. 이후 변경부터 시즌별로 독립해 보존한다.

### 다음 시즌 시작

다음 시즌 시작은 원본 시즌 경로에서 하나의 멱등 트랜잭션으로 처리한다.

1. 팀과 원본 시즌을 잠그고 접근 키와 상태를 검증한다.
2. 선택한 역할·반복 업무가 원본 시즌 소속인지 확인한다.
3. 선택한 반복 업무의 담당 역할이 선택한 역할 집합에 포함됐는지 확인한다.
4. 원본 시즌에 열린 역할 인수인계가 없는지 확인한다.
5. 원본 시즌을 종료한다.
6. 후속 시즌과 선택한 역할·반복 업무 스냅샷을 만든다.
7. 콘텐츠 생성 멱등 예약과 전체 결과를 함께 커밋한다.

역할·반복 업무 선택 목록은 순서가 의미 없는 집합이다. 중복을 거절하고 지문에서는 UUID를 정렬한다. 새 시즌 시작일은 원본 시즌 종료일보다 늦어야 한다. 같은 멱등 키와 같은 요청은 같은 후속 시즌과 복사 대응 관계를 반환하고, 같은 키의 다른 요청은 기존 멱등 충돌 계약을 따른다. 다른 키로 같은 원본 시즌에 두 번째 후속 시즌을 만들 수 없다.

### 동시성 경계

잠금 순서는 항상 `Team → Season`이다.

- 연속성 신호에 영향을 주지 않는 구성원 추가·이름 정정, 반복 업무 정의 생성·수정, 결정 변경: 팀 공유 잠금, 시즌 공유 잠금, 종료 여부 확인
- 연속성 신호에 영향을 주는 구성원 활동 상태, 역할·역할 인수인계, 회차·실행, 인수인계 항목·역할 자료, 반복 업무 보관·복원: 첫 원본 조회 전에 팀 공유 잠금, 시즌 배타 잠금, 종료 여부 확인
- 시즌 이름·기간 수정: 팀 공유 잠금, 시즌 배타 잠금
- 시즌 종료·재개: 팀 배타 잠금, 시즌 배타 잠금
- 다음 시즌 시작: 팀 배타 잠금, 원본 시즌 배타 잠금

BRIEF 시간 재조정도 `Team` 공유 잠금 뒤 `Season` 배타 잠금을 얻고 원본을 읽는다. 원본 변경과 신호 비교·불변 outbox 저장까지 이 잠금을 유지해 같은 시즌의 서로 다른 변경이 이전 원본 스냅샷으로 최신 신호를 되돌리지 않게 한다. 세부 생산 계약은 [PRD-0007](../../PRD/0007_brief-continuity-signal-producer/spec.md)을 따른다.

시즌 기간을 줄일 때 기존의 `null`이 아닌 회차 날짜, 역할 담당 기간이나 열린 역할 인수인계의 다음 담당 기간이 새 범위를 벗어나면 거절한다. `Season` 저장은 트랜잭션 종료 전에 플러시해 낙관적·비관적 잠금과 고유 제약 충돌을 애플리케이션 오류로 변환한다. 역할 인수인계와 역할·인수인계 항목·자료 사이의 세부 잠금은 ADR-0013을 따른다.

### 팀 접근 키

- 새 시즌은 기존 팀 접근 키를 그대로 사용하고 새 키를 발급하지 않는다.
- 어느 시즌에서 접근 키를 회전해도 같은 팀의 모든 시즌 링크가 함께 폐기된다.
- 신규 회전·복구 멱등 해시와 결과 키는 `teamId + idempotencyKey`로 파생한다.
- 기존 시즌 범위 파생으로 이미 시작한 대기 중 요청은 호환 동일 재처리 경로에서만 확인한다. 신규 요청의 권위 범위는 팀이다.
- 키 변경은 종료 시즌 경로에서도 허용한다. 이는 시즌 콘텐츠 변경이 아니라 팀 보안 동작이다.

### API와 조회 모델

- 워크스페이스 조회 모델은 현재 `season`과 함께 같은 팀의 서버 권위 `seasons` 목록을 반환한다.
- 목록은 시작일과 UUID 내림차순으로 결정적으로 정렬한다.
- 시즌 수정, 종료 상태 변경과 다음 시즌 시작 API를 제공한다.
- 다음 시즌 생성 응답은 원본·대상 시즌과 복사한 역할·반복 업무의 원본-대상 대응 관계를 반환하고 대상 워크스페이스를 `Location`으로 제공한다.

## 결과

- 과거 시즌의 역할, 인수인계, 자료, 회차, 실행과 결정이 새 시즌 변경으로 다시 쓰이지 않는다.
- 새 시즌은 필요한 운영 정의만 이어 받고 담당 배정과 실행 상태는 명시적으로 새로 시작한다.
- 종료와 콘텐츠 변경이 한 부모 잠금 경계에서 직렬화된다.
- 브라우저 최근 방문 기록이 아니라 서버 조회 모델이 시즌 탐색의 권위가 된다.
- 역할·반복 업무 복사와 계보 저장, 시즌별 조회 조건 때문에 스키마와 통합 테스트가 늘어난다.
- 기존 데이터에는 과거 시점별 역할 값과 종료 시각이 없으므로 이관 스냅샷과 종료 시각에는 위의 명시적인 한계가 있다.

## 대안

### 기존 역할 행을 모든 시즌에서 재사용

새 시즌 역할 수정이 과거 시즌의 목적, 책임, 담당자와 기간까지 바꾸므로 채택하지 않았다.

### 안정적인 팀 역할 식별성과 별도 시즌 스냅샷

시즌 간 동일 역할을 추적하기 쉽지만 현재 역할을 직접 참조하는 반복 업무, 결정, 인수인계, 자료의 외래 키와 애그리게이트를 모두 둘로 분리해야 한다. 현재 MVP의 계보 요구는 원본 역할 ID로 충족할 수 있어 이번에는 채택하지 않았다.

### 인수인계와 역할 자료도 다음 시즌에 자동 복사

복사 대상을 사용자가 고르지 못하고 보관·삭제가 제한된 중복 자료를 영구 생성할 수 있어 채택하지 않았다. 필요한 내용은 새 시즌 역할에서 명시적으로 다시 만든다.

### 종료일이 지나면 자동 종료

계획 날짜와 실제 운영 종료를 섞고 지연된 스터디를 예고 없이 읽기 전용으로 만들 수 있어 채택하지 않았다.

## 검증

- 기존 스키마에서 시즌 역할 소유권, 시즌 상태, 계보와 유일 제약으로 안전하게 이관되는지 확인한다.
- 종료 시즌 조회와 모든 콘텐츠 변경 거절, 접근 키 변경 허용을 확인한다.
- 시즌 기간 수정, 종료·재개와 후속 시즌 유일성을 확인한다.
- 선택 역할·반복 업무 복사, 담당 배정 초기화와 비복사 기록 보존을 확인한다.
- 같은 멱등 요청의 동일 재처리와 다른 요청 본문·동시 요청 충돌을 확인한다.
- 콘텐츠 변경과 종료·전환 트랜잭션의 경쟁이 부모 잠금으로 직렬화되는지 확인한다.
- 열린 역할 인수인계가 종료·전환을 막고 완료·취소한 역할 인수인계 이력이 새 시즌에 복사되지 않는지 확인한다.
- 같은 팀 키로 과거·현재 시즌을 전환하고 종료 시즌 UI가 모든 변경 진입점을 막는지 확인한다.
